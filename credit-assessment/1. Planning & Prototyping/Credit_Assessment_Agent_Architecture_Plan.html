Credit Assessment · Agent Architecture Plan

Five Agents for the Trade Credit Risk Tool

The document-to-decision pipeline, the calculation engines, and the governance services, organised as five owning agents that between them hold thirteen components — grounded in PRD v0.10. The five-agent split is the top layer; the component split beneath it is unchanged, and so is the fact that almost none of it is agentic. §03 draws the agent-vs-workflow line the way v1.9 did; one component of the thirteen is a genuine LLM agent, one is a hybrid, the other eleven are deterministic.

01 Summary & the five-agent model

The PRD describes one linear path with a human gate in the middle: upload statements (FR1) → extract a standardized field set with confidence and a source pointer per field (FR2) → a human confirms or amends every field against the source (FR3) → compute ratios (FR4) → score to a rating (FR5) → propose a limit and terms (FR6) → analyst submits, a different approver decides (FR7). Around that path sit services that make it defensible rather than advance it: the customer/assessment record (FR8), the audit trail (FR9), methodology configuration (FR10), export (FR11), and — from PRD v0.3, all Should/V2 — open-web adverse-media screening (FR12) with its screening-subject register (FR3.11), producing evidence a human weighs, never an input to the math.

That decomposes to thirteen components. This revision groups them under five owning agents, so the reader sees five domains, each holding the components that share its data, its trust boundary, and its release. The grouping changes no boundary the v1.9 plan drew — it adds a layer above them. A sixth agent is specified but not yet built — a read-only Q&A assistant (Agent 6, backed by PRD v0.11's FR13), the one place this architecture gains a second LLM agent:

What “agent” means here, and what it does not. These five are owning domains, each a home for one or more components. The word is used the way Sentinel and Atlas use it — a merged consolidation of finer-grained functions under one owner — not as a claim that each is LLM-driven. That distinction is load-bearing, because this system's whole traceability story (NFR Traceability: every rating reconstructable from source at any later date) rests on keeping non-deterministic models away from the math. So the grouping is deliberately drawn around that line, never across it: the one true LLM agent (FR12) and the one hybrid (FR2) each sit in an agent whose other contents are deterministic, and §03 states, per component, which is which. Grouping did not turn a workflow into an agent anywhere in the roster.
Why five, and why these five. The grouping follows the boundary test the v1.9 plan already used at the component level — entity ownership, transaction atomicity, shared trust boundary, and shared release — applied one level up. Agent 1 is everything that turns an uploaded document into extracted candidates (one atomic ingest-and-extract domain, holding MVP's only agentic capability). Agent 2 is the human confirmation gate, isolated because it is the single legitimate path into a ratio and the largest Must/MVP block of sub-requirements — the control the entire pipeline pivots on. Agent 3 is the three deterministic engines that share the versioned-config seam and the compute-on-write invariant. Agent 4 is the whole adverse-media domain — both its components are Should/V2, share the personal-data trust boundary, and one feeds the other. Agent 5 is everything that gates, records, configures, and exports, i.e. the governance and infrastructure every other agent writes through. Five is the natural count for the FR1–FR12 scope alone; the only thing that adds a sixth is a genuinely new capability — a conversational surface, now FR13 — which is why Agent 6 below is marked FR13 · V2, unbuilt rather than folded into the five (§02 records the two rejected sixths as well, both of which would have split existing work rather than added a capability).
Relationship to the Atlas plan — the five pipeline agents have no orchestrator; Agent 6 is one. Atlas is built around a chat orchestrator because its PRD specified one (FR8, five sub-requirements). This system's FR1–FR12 specify no chat, Q&A, or natural-language surface, so Agents 1–5 have no orchestrator tier: they are peer domains along a pipeline with a human gate, not workers under a coordinator. The FR12 screening agent is invoked by an event, not by a user asking a question, and returns records into a review queue rather than prose into a conversation — an agent, not an assistant. PRD v0.11 adds FR13, closely modelled on Atlas's FR8: a chat surface for users to query an assessment (ratios, rating drivers, case status, history, comparison) via Agent 6 (§02) — the one place this architecture gains an orchestrator, and a strictly read-only one, held to that by FR13.3 rather than by convention: it must never acquire write access to any entity in §11 or drive the pipeline agents to act. Unlike Atlas's orchestrator, which is the sole caller of task tools, Agent 6 calls no tool that mutates state at all.

02 The five agents and what each owns

Each agent, the components it owns, and the boundary reason those components belong together rather than apart. The detailed per-component behaviour is in §05–§09; this section is the map.

Agent 1 Statement Extraction

OWNS  Document Intake & Versioning · FR1 Field Extraction & Validation Routing · FR2

The document-understanding domain: accept a statement, version it, and extract a standardized field set with per-field confidence and a source pointer. Intake and Extraction are separate components — a batch machine step that runs once per document version versus a re-enterable interactive step — but one agent, because they form a single ingest pipeline over the same Document entity and hand off through one queue. This agent holds the system's only agentic capability at MVP (the extraction model, §03) and the one deterministic routing layer beneath it (the FR2.5 confidence floor). It also services FR1.7 copy-on-reuse and, at V2, FR2.8 screening-subject extraction — the same model capability over identity fields, sharing one evaluation harness. Detail: §05.

Agent 2 Field Review

OWNS  Field Review, Confirmation & Posting · FR3.1–FR3.10

The human confirmation gate, kept as its own agent for the reason it is the most important boundary in the system: FR3.8 makes it the only legitimate path from an extracted value into a ratio, and FR3 is the largest single block of Must/MVP sub-requirements. It owns one component that must succeed-or-fail atomically — set field status, retain the original on amend, normalize currency, version the record, fire the recompute (§06). Thin in component count, central in control. Why the screening-subject review (FR3.11) is not here, despite reusing this component's status grammar: opposite scoping invariant (field state never crosses an assessment boundary; a screening subject is deliberately customer-scoped and shared), no recompute to make atomic with, and a different completion gate — so it sits in Agent 4 (§08 boundary note).

Agent 3 Scoring & Decisioning

OWNS  Ratio Engine · FR4 Rating / Scorecard Engine · FR5 Recommendation Engine · FR6

The three strictly-sequential, entirely deterministic engines that turn confirmed fields into a decision proposal. One agent because they share the versioned-methodology seam (all three read config from day one, §07), the compute-on-write invariant (FR10.3: no engine may be a read-current-config service), and a chain in which each consumes the prior's output. They remain three components inside the one agent, not a merged calculator: they recompute on different triggers, ratios are a first-class UI output on their own (FR4.4 trend), FR5.3's V2 qualitative override would contaminate a merged engine, and FR6's sizing basis is OPEN on whether it needs inputs the scorecard never sees (§07). Detail: §07.

Agent 4 Adverse-Media Screening V2

OWNS  Screening Subject Register & Review · FR3.11 Adverse Media Screening · FR12

The entire adverse-media domain, isolated as one agent because both its components are Should/V2, both live inside the same personal-data trust boundary (NFR Personal data — adverse-media subjects), and one feeds the other: the register holds the customer's Confirmed/Amended roster of directors, UBOs, and guarantors, and only those rows become the screening agent's search scope (FR12.2). The two remain separate components because one is a deterministic human-review surface and the other is the roster's only pure LLM agent — open-ended judgement over unbounded, hostile, open-web input with no deterministic layer beneath it (§03, §08). This is the one agent whose name is literally true of part of its contents. Detail: §08.

Agent 5 Governance & Records

OWNS  Approval Workflow · FR7 Customer & Assessment Registry · FR8 Audit & Access Log · FR9 Methodology Config & Change-Control · FR10 Reporting & Export · FR11

Everything that decides an assessment, records it, configures it, and exports it — the governance and infrastructure layer every other agent writes through. Five components under one owner because they share a role: none advances a document toward a number; each gates, stamps, logs, versions, or renders. Two are pure infrastructure (Registry, Audit Log) that the other agents write through rather than call. This agent is heaviest by component count and lightest by novelty — state machines, append-only logs, versioned config, template fill. It is also where the Customer & Assessment Registry lives, which owns the three top-level entry points and the browse surface (§09). Detail: §09.

Agent 6 Assistant / Q&A Orchestrator FR13 · V2, unbuilt V2/V3

OWNS  Conversational Query & Answer · read-only, no FR yet

Planned, not committed — the one agent this architecture would add rather than regroup. A chat surface for a user to ask natural-language questions about an assessment: what a ratio is and how it was computed (its FR4.2 lineage), what drove the rating (FR5.2 breakdown), where the case sits in the workflow (FR7.1 state), what limit and terms were proposed or approved, and how this cycle compares to the last (FR8.8–FR8.9). It is the roster's second pure LLM agent (§03) — it interprets open-ended intent, which none of the five deterministic-or-single-purpose agents can do — and it is why the plan can no longer say “no orchestrator” unconditionally.

Read-only by hard rule — an orchestrator of reads, never of tasks. It composes answers from the stored outputs of Agent 3 (Ratio, Rating, Recommendation) and Agent 5 (Registry state, approval status), each fetched under the caller's existing RBAC scope (NFR Confidentiality/RBAC, applied before the query reaches data). It has no write path to any entity in §11, invokes no engine's computation, and advances no workflow state — so it cannot bypass the FR3.8 human gate or FR7.5 segregation of duties. An action a user asks for in chat (“refresh this customer”) at most pre-fills and navigates into the existing gated flow, exactly as FR8.11's Refresh-this-customer route does; the irreversible step still happens through the owning agent with its human in the loop. This is a deliberate departure from Atlas, whose orchestrator is allowed to call task tools — that fits Atlas's design, not this maker-checker pipeline.

Grounded-or-refuse, and its own eval harness. Every claim cites a stored value or says the data is not available; it never invents a ratio, a grade, or a status, and its answers explain what the system computed rather than recommend or decide (FR13.4–FR13.6). Grounding is a fixed set of parameterized queries, never free-text search or a vector index over assessment content (FR13.11) — so a citation is verifiable by construction, and the eval harness scores query-selection accuracy and refusal correctness rather than open-ended retrieval quality. Once FR12 ships it may also summarize screening status and Relevant findings, gated the same way (FR13.10). Specified as FR13 (PRD v0.12, Should/V2, eleven sub-requirements, all three of v0.11's open decisions now closed) — scope, grounding sources, citation format, and the route-not-execute fallback are all written down, closely modelled on Atlas's FR8. Not yet built: nothing blocks starting except prioritisation against the rest of V2. Build order and guardrails: §10, §12.

Two grouping calls worth stating, both resolved in favour of five. (a) Should Field Review fold into Statement Extraction, as Atlas folds human validation into its DocAnalyst? No — Atlas made that call for its own pipeline, but here the confirmation gate carries the segregation-of-duties-adjacent control weight (FR3.8/FR3.10 block submission and bar the Recommendation Engine), and burying the system's single legitimate path-into-a-ratio inside the extraction agent would hide the control the whole plan pivots on. Kept visible as its own agent. (b) Should the two infra components (Registry, Audit Log) be their own agent rather than sitting inside Governance & Records? They could, and that would make a sixth. Rejected because it buys nothing the reader needs: both are written-through by every other agent, both are governance in the plain sense, and a standalone “infra” agent holding two append-only stores is a layer diagram, not an owning domain. Both rejected sixths would have split existing work; the one accepted sixth (Agent 6, above) adds a capability the current PRD lacks. That is the line: a sixth agent is justified by new intent to interpret, never by redistributing the thirteen components differently.

03 Agent vs. workflow — what actually needs an LLM

The five-agent grouping is an ownership layer; it does not change what is or is not agentic. The PRD is titled “GUI + Agentic Backend” and calls FR2 an “agentic pipeline,” which reads as a system full of agents. It isn't. The two categories have different engineering needs: real agents need prompt design, an evaluation harness, and human-in-the-loop guardrails; workflows just need to be correct, fast, and covered by ordinary tests.

The test: does the component exercise judgement over ambiguous or unstructured input — interpret a layout it has never seen, choose between plausible readings, infer meaning from free text — or is it a fixed sequence with one correct answer given the input? For the calculation engines, being the second kind is a requirement: FR4.2 demands full lineage to exact source values and NFR Traceability demands every rating be reconstructable at any later date. Both argue against a non-deterministic model anywhere near the math.

Naming — only Agent 4's inner component (and, when built, Agent 6's) carries the word Agent; everything else is an Engine, Workflow, Registry, or Log. Ten components need ordinary tests; two need evaluation infrastructure today, a third (Agent 6) when chat is built — each inside an agent whose name hints at it.

05 Agent 1 · Statement Extraction

FR1–FR2 plus FR1.7–FR1.9's provenance rules. Two components, one ingest pipeline. Only the extraction step is agentic (§03); no component here writes a value into a ratio-eligible state on its own — every path ends at a human confirming a field in Agent 2.

Why Intake and Extraction are two components under one agent. The boundary that holds between them: extraction is a batch machine step that runs once per document version per assessment and never mutates after; intake is the scan/store/version front door. Different units of work with a queue handoff — so two components. But they share the Document entity, the same trust boundary (customer-supplied input), and the same MVP release, and neither is meaningful without the other — so one agent. This is also where MVP's only model-bearing surface lives, which is why the extraction evaluation harness is built here (§12, MVP 2).



Copy-on-reuse (FR1.7), and why every copied field resets to Unconfirmed. On reuse of a prior-period statement by a new assessment, Intake attaches the reference and raises the reuse event; Extraction writes the copied rows (it owns ExtractedField creation everywhere else, §11) with no model invoked — a copy is a deterministic write. The status reset is the load-bearing half: carrying a field forward at Confirmed would let one assessment's review satisfy another's human-confirmation requirement (FR3.4/FR3.8) against a different period set, possibly by someone with no role on the second file. Same values, confidences, pointers, and model version; status back to Unconfirmed; review runs again. ExtractedField belongs to Assessment, not Document — document_id is provenance only (FR1.7, corrected at PRD v0.6).

08 Agent 4 · Adverse-Media Screening V2

FR3.11 and FR12, both Should/V2. The whole adverse-media domain: a customer-level roster of natural persons, and the open-web agent that screens them. This agent gathers evidence a human may weigh against a decision — it advances no document toward a number (FR12.6) and feeds no engine.

Why the register and the agent are two components under one owner. They share the personal-data trust boundary and the V2 release, and the register exists for the agent — only Confirmed/Amended subjects become its search scope (FR12.2). But one is a deterministic human-review surface and the other is a pure LLM agent over hostile open-web input, so they stay separate components with different engineering (the agent carries an evaluation harness; the register carries ordinary tests). Why the register is not part of Agent 2's Field Review, despite the identical status grammar: opposite scoping invariant — ScreeningSubject belongs to Customer and is shared across every assessment, the inverse of the field-state-never-crosses-an-assessment guarantee (§10); no recompute to make atomic with; and a different completion gate (an Unconfirmed subject narrows FR12.2's scope but blocks no submission). Housing both in Agent 2 would invite applying FR1.7's copy-on-reuse to a roster that must not be copied.
The screening trigger, the human gate, and the frozen-snapshot rule. FR12.1 fires the agent once, the moment FR4 ratio computation completes — the earliest point an assessment-scoped run is meaningful, and the maximum lead time before FR5.3, the only window a finding can be cited (FR12.6). It gates nothing: PRD §2.12 bars any release from making FR5/FR6 depend on FR12, so it runs advisory and asynchronous and the FR1→FR7 path completes whether or not screening returned. Every finding goes to a human, who marks it Relevant, Not Relevant, or Needs Follow-up (FR12.5); only Relevant may be cited (FR12.6); there is no edge from the agent to any engine. And because web retrieval cannot be reproduced on re-run — the index shifts, pages are edited or deleted — an AdverseFinding is a frozen snapshot captured at the run, belonging to a ScreeningRun, never re-fetched to redisplay (§10).

10 Cross-cutting guardrails

These apply to every component in every agent, agentic or not:

Validation gate: no component may treat an Unconfirmed field as fact. FR3.8 mandates Provisional marking (exclusion would silently change what a formula measured), and FR3.10 gives it teeth — submission is blocked while any Provisional result stands, and a Provisional rating never reaches the Recommendation Engine.
A stated non-computation is not a value, and not Provisional either. A required line item genuinely absent (Not Present) makes its ratio Not Calculable, a third terminal state. Three rules hold wherever the value is rendered, stored, or consumed: (1) never substitute — no zero, no partial computation, no carry-forward; store null. (2) Never conflate with Provisional — mutually exclusive, Not Present wins; they mean opposite things about what a reviewer does next and carry opposite submission consequences. (3) Never render as a gap — visibly distinct from a computed value, from Provisional, and from not-yet-computed. OPEN — how the scorecard consumes it (§12); until answered the Rating Engine propagates the state rather than coercing it to a number.
Field state never crosses an assessment boundary. ExtractedField belongs to Assessment; no confirm, amend, or recompute in one assessment may change what another shows, even citing the same statement, even when one is Approved and closed. Enforced structurally — reuse copies the fields (FR1.7) and every copy resets to Unconfirmed. The one deliberate exemption is ScreeningSubject, which belongs to Customer and is shared across assessments — a director is a fact about the entity, not a reading of one statement. Reading across the boundary is not crossing it: FR8.5/FR8.6/FR8.8–FR8.9 read a second assessment's rows and change nothing; the reflex to guard against is re-deriving a closed assessment's ratios under the current config to make them “comparable,” which rescores it and breaks FR10.3. State a config difference alongside the delta; never remove it.
Never silently overwrite: document re-upload creates a new version (FR1.5), field amendment retains the original (FR3.6), a Refresh creates a new linked version rather than editing the last (FR8.2–FR8.4), and copy-on-reuse isolates fields per assessment (FR1.7). Each is paired with an audit entry (FR9.1).
Segregation of duties: approver ≠ preparing analyst, enforced by the system at both submit and decision time (FR7.5). FR7.6 sets block-by-default when no eligible second approver exists, any break-glass path an audited exception. OPEN: the delegation model (§12).
Config immutability for historical results: a methodology change must never retroactively rescore a past assessment (FR10.3). The three engines cannot be read-current-config services — each writes an immutable result stamped with the config version that produced it (FR4.5, compute on write). A config version must outlive every assessment computed under it (§11).
Reconstructability, not just lineage: NFR Traceability requires four things to survive together for the retention period — the source document, the field-level source pointer, the config version, and the extraction model/prompt version (FR2.7, ExtractedField.extraction_model_version) — or a model upgrade makes a past extraction unreproducible even with every value intact.
The recommendation is a proposal, never an application: nothing downstream may apply a limit or terms to a live account without an FR7.4 approval (FR6.2). The guardrail most at risk from the OPEN ERP/CRM integration — whichever component eventually writes a limit outward must read Approved state only and be the sole path out.
Role-scoped visibility: scope every query by the caller's role before it reaches data, not at the UI layer (NFR RBAC, FR9.3). Still unresolved: director names, signatures, and guarantor details appear in audited accounts and the FR3.3 viewer shows the raw page to anyone holding the field; v0.6 raises the stakes by lifting those names into ScreeningSubject as queryable records, and v0.9 adds the Customer Directory, which scopes an aggregate — the filter must run before the per-customer rollup, not over its output. A masking decision must cover all four surfaces (viewer, exports, register, directory) at once, or explicitly find none is required (§12).
Currency is normalized explicitly or blocked, never assumed: ratios are only comparable within one currency, but FX normalization stays OPEN — reject a mixed-currency assessment rather than normalize with an unspecified rate at an unspecified date. Enforced by Agent 2.
Untrusted external content — the first input the system takes from outside its own trust boundary (Agent 4). (1) Adversarial by default: retrieved content reaches the model as data, never instruction; a page's claims stay claims — a finding says a named source alleges X, never that X is true, which is why the source URL is mandatory. (2) No path around the human, none into the math: FR12.5 forces review, FR12.6 restricts citation to Relevant, and no edge runs from screening to any engine. (3) A finding is a frozen snapshot, not a live query: captured and stored at the run, never re-fetched — the one workload here that cannot be reproduced on re-run.
The Q&A assistant reads, cites, and refuses — it never acts (Agent 6 / FR13, when built). Three rules, mirroring the guardrails above for a surface that answers questions rather than computing values. (1) Read-only and role-scoped: it composes from stored engine and Registry outputs under the caller's existing RBAC scope, applied before any query reaches data; it holds no write path to any entity in §11 and triggers no computation or state transition, so it cannot bypass the FR3.8 human gate or FR7.5 segregation of duties. An action a user requests in chat pre-fills and navigates into the owning agent's gated flow (the FR8.11 Refresh-this-customer pattern) — it never executes the irreversible step. (2) Grounded or refuse: every claim cites a stored value — a ratio, a field, a decision — or states the data is unavailable; it never infers a number, a grade, or a status the system did not compute, and it explains what was computed rather than recommending. Answers stamp the config version behind any cited rating, so a figure quoted in chat means the same as the same figure in the report (FR10.3, FR11.2). (3) A grounded answer is not a decision: nothing the assistant says finalises a limit, advances an approval, or substitutes for the FR7 workflow — it is a read of the record, held to the same standard as the FR3.3 source jump: a claim is usable only if a human can reach what produced it.

Retention: four clocks at MVP, five at V2. (1) the assessment cycle — the only mutable window; (2) the credit-limit clock — an approved limit stays live until superseded, FR8.7 records the effective date, expiry cadence OPEN; (3) the regulatory retention clock — duration and jurisdiction OPEN, so no component implements disposal, but the derived constraints hold (documents outlive the assessments citing them; configs outlive every assessment computed under them); (4) the audit clock — never prunes in normal operation.
