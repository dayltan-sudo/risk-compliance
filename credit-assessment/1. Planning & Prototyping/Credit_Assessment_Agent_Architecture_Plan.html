01 Summary of the approach

The PRD describes one linear path with a human gate in the middle: upload statements (FR1) → extract a standardized field set with confidence and a source pointer per field (FR2) → a human confirms or amends every field against the source document (FR3) → compute ratios (FR4) → score to a rating (FR5) → propose a limit and terms (FR6) → analyst submits, a different approver decides (FR7). Around that path sit four services that exist to make the path defensible rather than to advance it: the customer/assessment record (FR8), the audit trail (FR9), methodology configuration (FR10), and export (FR11). PRD v0.3 added a fifth (FR12, Should/V2): open-web adverse-media screening whose output is evidence for a human to weigh, never an input to the math. PRD v0.6 moves that screening's trigger off the submission event to the moment FR4 finishes computing ratios, and gives FR12 the input it previously assumed — a customer-level roster of directors, UBOs, and guarantors, sourced from a new registration document (FR1.8), extracted in tiered fallback (FR2.8), and confirmed on its own review surface (FR3.11). PRD v0.7 then widens FR8 — the customer/assessment record — from a passive store into the surface an assessment is started from: FR8.3 makes the New-vs-Refresh entry point explicit, FR8.5 adds read-only drill-down into any prior assessment, and FR8.8–FR8.9 add a delta view over two assessments' already-computed outputs. PRD v0.9 widens FR8 once more, and this time along a different axis: FR8.10's Customer Directory is a way into the system that starts no assessment at all — a third top-level entry point beside FR8.3 and FR7 — with FR8.11's customer detail view and FR1.9's document browsing behind it. PRD v0.10 connects that third entry point to the first: FR8.11's Refresh this customer routes a rights-holding analyst into FR8.3's refresh flow with the customer, and where applicable the viewed assessment, pre-selected — browse is still the mode that writes nothing, but it is no longer a dead end.

That maps onto 13 components in three tiers: a three-component document-to-decision pipeline that ends at a posted, human-confirmed record; three sequential calculation engines that turn confirmed fields into a decision proposal; and seven governance, evidence, and records components that gate, screen, log, configure, and export. Every component is described against its FR range in §04–§06.

Boundary review (v1.6, against v0.7's FR8.3–FR8.9): does the comparison belong to the Registry or to the three engines? The tempting split, and the one to refuse. FR8.8–FR8.9 read Ratio, Rating, and Recommendation — three entities the Registry neither owns nor computes, each owned by a §05 engine that is the “single place that entity's logic lives.” On subject matter alone the comparison splits three ways. This plan's boundary test is not subject matter: it is entity ownership, transaction atomicity, and the engineering the component needs. All three point at the Registry.

(a) It owns no entity, so entity ownership does not select an engine. PRD §4's Assessment row is explicit — the comparison “reads two Assessment records' already-stored Ratio/Rating/Recommendation rows directly at view time — no new entity required.” The engines are defined by what they write: FR4.5's compute-on-write, FR5's stamped result, FR6's proposal. A read-only view that writes nothing has no entity to hang on an engine, and giving one a second output shape that isn't its entity is the shape §05 was drawn to avoid.

(b) The engines are single-assessment by invariant, in both directions. FR4.3's recompute is scoped to the amending assessment and “cannot reach into another assessment sharing the same source document” — the §07 guardrail. A cross-assessment read is safe in itself, but putting the system's only cross-assessment code path inside the component that must never have a cross-assessment write path is a poor place to put it. Keeping the engines assessment-scoped in every direction is the cheaper invariant to hold, and the one a reviewer can check by inspection.

(c) The Registry already does this, one level coarser. FR8.6's history view — prior ratings and limits over time — is already a cross-assessment read of Rating and Recommendation output, already in the Registry's remit, already described here as “a cross-assessment read no single-assessment component can answer.” FR8.8–FR8.9 is that same read at finer grain over exactly two assessments, plus subtraction. It extends a capability rather than founding one.

(d) The two governing rules are one implementation, not three. FR8.8's config-version annotation and its Provisional/Not-Calculable suppression apply identically to ratios, rating, and recommendation (FR8.9 says so). Split across three engines they are written three times, and the first divergence between the copies is a delta presented as like-for-like across a methodology change — the exact failure FR8.8 rule 1 exists to prevent.

(e) Nothing in it needs an engine's engineering. A delta is subtraction and a direction label. It needs no formula config, no scorecard, no sizing rule — and it does need customer-scoped assessment lookup, which only the Registry has. The rules read three stamps the engines already wrote (provisional_flag, not_calculable_flag, config_version_id), so the Registry applies them without knowing what any ratio means.

The one place ratio semantics do enter, and why it does not change the answer. FR8.9's rating-grade movement needs grade order, which lives in ScorecardConfig's band sequence (FR10.1). The Registry reads it as data, becoming a fourth reader of the config seam and no kind of writer. Where the two assessments' config versions differ, FR8.8 rule 1 fires and the movement is stated as prior grade to new grade under a declared methodology change — never asserted as an improvement. The condition that would reopen this call: a future requirement asking the comparison to judge a delta as favourable or adverse. That is methodology, and while it would still be config the Registry reads rather than logic it owns, it is the point at which “a delta is arithmetic” stops being true and this boundary should be re-tested.

Rejected alternative: a standalone Assessment Comparison component. It would own no entity, hold no state, run no model, and need no harness — a view over two other components' rows, with a customer-scoped lookup it would have to reimplement or call the Registry for. That is a function, not a component, and adding it would break the count for nothing.

Boundary review (v1.8, against v0.9's FR1.9 / FR8.10 / FR8.11): does document browsing belong to the Registry or to Document Intake & Versioning? FR8.10 and FR8.11 are not seriously in doubt — they read Customer and the assessment version chain, which the Registry owns outright, and FR8.10 is FR8.6's data condensed to its latest point and widened from one customer to all of them. FR1.9 is the real call. It reads the Document entity, and Document Intake & Versioning is that entity's write owner (§08) and the home of the whole FR1 family. Subject matter says Intake. This plan's boundary test says otherwise, on the same four grounds that put FR8.8–FR8.9 in the Registry rather than in three engines.

(a) Entity ownership is write ownership, and FR1.9 writes nothing. §08 states this directly and v1.6 already relied on it: a read confers no ownership and no mutability. FR1.9 mints no document, versions nothing, and takes “no action on any assessment” in its own words. On the same reasoning that a read-only delta had no entity to hang on an engine, a read-only document list has none to hang on Intake.

(b) Half of FR1.9 is a cross-assessment read Intake cannot answer. The requirement has two halves: the version chain for a document (FR1.5, squarely Intake's data) and every assessment that currently references that document (FR1.6's many-to-many). The second half is a lookup over the assessment side of that relationship, scoped to a customer — the capability §06 already describes as “a cross-assessment read no single-assessment component can answer,” and the reason FR8.5, FR8.6, and FR8.8–FR8.9 sit in the Registry. Intake is document-scoped and upload-triggered; it has no customer-scoped assessment lookup and would have to reimplement one or call the Registry for it.

(c) Splitting FR8.11 would put one screen's role scope in two components. FR8.11 assembles three things under one access rule — FR8.6's trend, FR8.5's drill-down, and FR1.9's documents, “scoped by the same role rules as FR8.10.” Serve two of the three from the Registry and the third from Intake, and the FR8.10 scope rule is implemented twice, against NFR RBAC's requirement to scope every query by role before it reaches data. The first divergence between the two copies is an Analyst seeing a document list referencing assessments their own directory row is filtered to exclude. This is argument (d) from the v1.6 review in a new place: two copies of one rule, and the first drift is the failure the rule exists to prevent.

(d) Nothing in it needs intake engineering. Intake's job is virus-scan, encrypt, assign an ID, capture FR1.4 metadata, mint a version. FR1.9 needs none of them. It needs customer-scoped lookup and a join across the FR1.6 relationship — and it fails §04's defining property outright, since it advances no document toward a number. That is the same test that put FR12 and FR3.11 in §06 rather than in the pipeline, applied to a read surface.

The counter-argument, and why it does not decide it. PRD v0.9 places FR1.9 under FR1 deliberately, so the Document entity's own family owns the content once and FR8.11 cross-references it. That is a documentation-structure decision about where a requirement is stated, not about which component serves it, and this plan has ruled the same way twice before in both directions: FR3.11 sits in the FR3 family but is a separate component from Field Review, and FR1.7 sits in the FR1 family but its rows are written by Field Extraction. FR-family membership has never selected a component here.

What the decision costs, stated plainly. The Registry becomes a reader of Document, its fifth read-only dependency after Ratio, Rating, Recommendation, and ScorecardConfig. That is the price, and it is the same price v1.6 accepted. It buys a single owner for one screen, one implementation of one role-scope rule, and no new component. The condition that would reopen this call: a requirement that lets a user act on a document from the browse surface — supersede a version, detach a reference, upload a replacement in place. That is an intake write, it belongs to Intake, and FR8.11's in-place read-only clause is currently the only thing keeping it out — undisturbed by PRD v0.10's Refresh this customer route, which mutates no document and edits nothing on the view.

Rejected alternative: a standalone Customer Directory / History Browser component. It would own no entity, hold no state, run no model, need no harness, and would reimplement the customer-scoped lookup and the RBAC scope the Registry already has — word for word the v1.6 rejection of a standalone Assessment Comparison component. A function, not a component.
Deliberate scope difference from the Atlas plan — no conversational assistant. Atlas is built around a chat orchestrator because Atlas's PRD specified one (its FR8: page-aware prompts, live-data answering, citations, fallback behaviour). This PRD specifies no chat, Q&A, or natural-language surface anywhere in FR1–FR12 — its FR8 is the customer/assessment record, and §0.1 puts portfolio-level analytics out of scope explicitly. So this architecture has no orchestrator tier and no grounding-services tier: it is a pipeline with a human gate, not an assistant with retrieval behind it. Unchanged by FR12 — the new screening agent (§06) retrieves from the open web, but it is invoked by an event, not by a user asking a question, and it returns records into a review queue rather than prose into a conversation. An agent, not an assistant. This is a scoping decision, not an omission. A conversational layer over approved assessments (“which customers dropped a grade this quarter?”) is a natural V2/V3 addition and would slot in as a read-only consumer of the Ratio, Rating, and Registry components — but it needs a requirement in a future PRD revision first, and it must not acquire write access to any entity in §08 if added.

Judgement over ambiguous document layout: yes — deciding that a name on a signing page is a director rather than an auditor or company secretary is the same class of problem as mapping an arbitrary line-item label to a standardized field. Deterministic layer beneath: yes, and now two of them — FR2.5's confidence floor plus FR2.8's tier ladder, which is a fixed rule with one correct outcome (if no candidate for role R in tier n: try tier n+1), triggered on absence, explicitly not on low confidence. FR3.11 (screening-subject review) → a new component: Screening Subject Register & Review (§06). The tempting merge, and the one to refuse. It reuses Field Review's status grammar verbatim (Confirm / Amend / Not Present, confidence indicator, source jump), which is a UI similarity, not a boundary argument. Four things push the other way, and the first is decisive. (a) Opposite scoping invariant. After v0.6, Field Review's defining guarantee is that field state never crosses an assessment boundary — that is the whole content of FR1.7 and the reason FR8.2's per-field promise holds. ScreeningSubject is deliberately the inverse: customer-scoped, shared across every assessment, never copied per assessment. Housing both in one component invites precisely the wrong reflex — applying FR1.7's copy-on-reuse to a roster that must not be copied. (b) No atomicity binding. The merge that created Field Review rested on FR4.3: a confirm must set status and fire the recompute in one transaction. Confirming a screening subject fires no recompute and touches no Ratio; it changes which rows FR12.2 will search at the next run. Nothing to make atomic with anything Field Review owns. (c) Different completion semantics. An unreviewed financial field blocks submission through its Provisional ratio (FR3.10); an Unconfirmed screening subject blocks nothing and simply narrows FR12.2's scope. Two gate rules in one component's progress model is a defect waiting to happen. (d) Release risk. FR3.11 is Should/V2 and exists only to serve FR12; Field Review is the largest Must/MVP block in the roster. Merging puts MVP's core GUI behind a V2 dependency — the same objection §06 already uses to keep Approval Workflow and Methodology Config apart.

The asymmetry is deliberate. FR2.8's extraction folds in while FR3.11's review does not, even though they handle the same entity, because they are drawn by different criteria: extraction components are drawn by model capability and eval harness (identical), review components by entity scope, transaction, and gate rule (opposite).

02 Agent vs. workflow — what actually needs an LLM

The PRD is titled “GUI + Agentic Backend” and calls FR2 an “agentic pipeline.” Taken literally that reads as a system full of agents. It isn't. Worth separating cleanly, because the two categories have different engineering needs: agents need prompt design, an evaluation harness, and human-in-the-loop guardrails; workflows just need to be correct, fast, and covered by ordinary tests.

The test: does this component have to exercise judgement over ambiguous or unstructured input — interpret a layout it has never seen, choose between plausible readings, infer meaning from free text — or is it a fixed sequence of steps with one correct answer given the input? For the calculation engines here, being the second kind is a requirement, not a shortfall: FR4.2 demands full lineage to exact source values and NFR Traceability demands every rating be reconstructable at any later date. Both are arguments against putting a non-deterministic model anywhere near the math.

Applied to PRD v0.3's FR12, the test returns the first answer with nothing deterministic underneath it — which is new. Extraction is a hybrid because a fixed rule sits beneath the judgement (FR2.5's confidence floor: one comparison, one correct outcome). Screening has no such layer: the input is the open web rather than a supplied document, there is no ground-truth answer to converge on, and every step is a call — whether a hit concerns this subject or a namesake, whether the content is adverse in FR12.3's sense, how material it is, what relevance score to attach (FR12.4). Trigger, persistence, and audit logging sit around it, but every component in this roster has those; they are not a deterministic half.

(4) Naming — “Agent” appears in exactly one component name, and that is the signal: everything else is an Engine, Workflow, Service, Registry, or Log. The hybrid keeps its non-agent name because half of it is a threshold rule, and the new Screening Subject Register keeps a records name because it holds decisions rather than making them. Two components need evaluation infrastructure; eleven need ordinary tests.

Unchanged at v1.8, and tested rather than assumed. 04 Document-to-decision pipeline

FR1–FR3.10, three components — FR3.11's screening-subject review is not one of them, and sits in §06 (§01 boundary review). Of these three, only the extraction step inside the second is agentic (§02); the roster's other model-bearing component sits in §06. No component here writes a value into a ratio-eligible state on its own; every path ends at a human confirming or amending a field against the source document.

Merged FR3's review surface with enrichment and posting. The first pass had these as two components: a Field Review & Confirmation service owning the FR3.7 status lifecycle, and an Enrichment & Posting workflow doing currency normalization, the versioned write, and the recompute trigger. They are one component, on the same atomicity argument Atlas used for its own posting stage: FR4.3 requires ratios to recompute automatically whenever an underlying field is later amended, so a single confirm-or-amend action must atomically set the field's status, append its amendment history with the original value and confidence retained (FR3.6), write the audit entry (FR9.1), normalize currency, version the confirmed record, and fire the recompute. Split across two services, a lost message between them yields the worst available failure mode — a field that looks Confirmed next to ratios computed from its old value, with nothing on screen to indicate the mismatch. One component, one transaction, no such state.

The corresponding boundary that does hold is between extraction and review: extraction is a batch machine step that runs once per document version per assessment and never mutates afterward; review is an interactive human step that can be re-entered days later. Different owners of different fields on the same entity, with a queue handoff between them — not the same unit of work.

The scope qualifier in that sentence is new at v1.5 and it is not cosmetic. Through v1.4 this plan described a field set as following the document version that produced it. PRD v0.6's FR1.7 makes that wrong: ExtractedField belongs to Assessment, with document_id retained as provenance only, so the same statement referenced by two assessments yields two independent field sets. The rule that produces the second one is below.
Copy-on-reuse, and why every copied field resets to Unconfirmed (FR1.7). FR1.6's many-to-many Document–Assessment relationship — a correction this plan raised at v1.0 and PRD v0.2 made — solved document duplication but left the field-level half undone until v0.6. Under the old shape, a prior-period statement reused by a new assessment brought its fields along too, so an analyst confirming a value in the new assessment mutated a record that an older, possibly already Approved, assessment had cited — violating FR8.2's never-overwrite guarantee silently, and changing a closed assessment's lineage after the fact. FR1.7's fix: on reuse, copy the document's most recent extraction into the referencing assessment's own scope and re-run no model, because nothing about the document changed.

The copy is not enough on its own; the status reset is the load-bearing half. Carrying a field forward at Confirmed would let one analyst's review, in one assessment, satisfy a different assessment's human-confirmation requirement (FR3.4, FR3.8) — the confirmation would be real but it would be a confirmation of a different decision, made against a different period set, possibly by a person with no role on the second file. FR3.10's submission gate would then pass on evidence nobody in that assessment produced. So: same values, same confidences, same source pointers, same extraction_model_version; status back to Unconfirmed; review runs again.

Which component performs it. Document Intake attaches the reference and raises the reuse event; Field Extraction & Validation Routing writes the copied rows, because it owns ExtractedField creation everywhere else (§08) and splitting that ownership would give two components two ways to mint a field. The distinction from a normal extraction pass is that no model is invoked — a copy is a deterministic write, and it belongs to the component's workflow half, not its agentic one. Cost is FR1.7's stated reason; reproducibility is the stronger one, since a re-run against a newer model would produce values that differ from the ones the first assessment was decided on.
The registration document sub-flow — three intake behaviours to skip, not adapt (FR1.8, Should/V2). It is the same Document entity in PRD §4, distinguished by a type value with period and currency null, which is why it folds into this component rather than founding another (§01 boundary review). The differences are all subtractive, and each is a step the financial-statement path runs that this one must not:

(1) No assessment link. Every financial-statement upload opens or attaches to an assessment version in the Registry. A registration document does not — it belongs to the Customer and is referenced by no Assessment at all (PRD §4 Document). (2) No period, no currency, no statement type. FR1.4's metadata set applies only in the subset FR1.8 names; FR1.2's audited/unaudited tag is explicitly not asked for, so intake must not require it. (3) Re-upload is triggered by a registration change, not a fiscal year. FR1.3's multi-period logic has nothing to act on; FR1.5's new-version rule still applies unchanged.

The consumer is FR2.8's tier 2, and nothing else in the system reads it. If it is absent, tier 2 is simply unavailable and FR2.8 falls through to manual entry — the document is optional input to a Should/V2 path, never a precondition for an assessment.

FR4–FR6, three components, strictly sequential and entirely deterministic. Each owns one entity in PRD §4 and is the single place that entity's logic lives. All three consume a versioned methodology config rather than hard-coded rules — see the callout below and §09.

Two merges considered and rejected. Ratio + Rating: at MVP the Rating's only inputs are ratios (FR5 ships quantitative-only), so the usual “external drivers” argument for separation doesn't yet apply — but three things separate them anyway. Recommendation also owns a different entity with its own override-plus-justification behaviour (FR6.3) and is the output the approval locks (FR7.4). Keep it outside the scorecard until that question is answered; merging now would have to be undone if the answer is “also exposure-based.”

06 Governance, evidence & records components

These don't advance an assessment toward a number — they decide it, record it, configure it, export it, and (from PRD v0.3) gather outside evidence a human may weigh against it. Seven components. Two are infrastructure other components write through rather than destinations of their own. Six are deterministic; the seventh is the roster's only pure agent.

Two merges considered and rejected here. Approval Workflow + Methodology Config & Change-Control: both are approval-gated state machines and the shapes rhyme (Draft → Submitted → Approved vs. edit → review → approve → version), which is the most tempting merge in this roster. Rejected on three counts — different actor populations with different segregation rules (Analyst vs. Approver on one transaction per FR7.5; Config Admin against an approver population the PRD hasn't named at all), different blast radius (one customer's limit vs. every future assessment's methodology), and different release with different blockers (FR7 is Must/MVP and unblocked; FR10 is Should/V2 and blocked on the baseline template). Merging would put MVP's critical path behind a V2 dependency. Config Change-Control + Audit & Access Log: rejected for the same reason the Atlas plan rejected it — one is an active, business-specific workflow, the other is passive, universal infrastructure every component writes to; collapsing them buries generic audit logging inside one workflow's approval logic.

Approval Workflow

Workflow Must MVP

Owns the Draft → Submitted → Approved | Rejected | Returned for Revision state machine (FR7.1) and the visibility rule that only a Submitted assessment reaches an Approver (FR7.2). Grants the Approver read access to the full extraction, ratio, and rating lineage plus the audit trail (FR7.3). On Approve, locks the final limit and terms; on Reject, closes the assessment with a required reason; on Return, sends it back with comments and re-enters Draft (FR7.4) at the Field Review component. Enforces approver ≠ preparing analyst in the system, not the process, at both submission and decision time (FR7.5). FR7.6 now carries the block-by-default rule when no eligible second approver exists, with any delegation or break-glass path as an audited exception — the delegation model itself stays open (§09). Multi-approver committee with a majority or unanimous rule is Could/V2 (FR7.7); PRD v0.2 models ApprovalDecision as a collection from MVP so this needs no migration.

FR7.1–FR7.7 · §4 Assessment, ApprovalDecision

Customer & Assessment Registry

Infra Must MVP

Owns the Customer entity — master data that outlives every assessment and that no pipeline component has a claim on — and the assessment version chain: one customer, many assessments, each versioned and never overwritten (FR8.1–FR8.2). Kept rather than folded into Intake and Approval Workflow because those two would otherwise both mint versions under their own rules; the never-overwrite invariant needs exactly one enforcement point. Classified infra, not workflow: it holds no business decision.

The entry point is a Registry read, not an analyst preference (FR8.3, v0.7). It evaluates the customer's prior-assessment count and offers exactly one path: New at zero priors, minting version 1 with an empty field scope; Refresh at one or more, capturing a source assessment (defaulting to the most recent) and minting version n+1 linked to it. No other component can count a customer's assessments, and no assessment exists yet to hold the question. It mints the record in Draft; every transition out of Draft belongs to the Approval Workflow (§08). Refresh then hands the source's prior-period document references to Document Intake, which raises FR1.7's reuse event exactly as it does on an upload-attach — the Registry never becomes a second writer of ExtractedField (§04, §03).

Three cross-assessment reads, none of which writes anything. FR8.5 opens any prior assessment — not only a refresh source — read-only at its last-recorded field, ratio, rating, and recommendation state, and never reopens it for editing. FR8.6 serves the per-customer summary trend of prior ratings and limits over time. FR8.8–FR8.9 compute the delta between this assessment's freshly computed outputs and the refresh source's stored ones: direction and magnitude per ratio, grade movement, and the limit and terms change. All three are reads no single-assessment component can answer, which is why they sit here (§01 boundary review).

From v0.9 it is also the browse surface — a third top-level entry point, not a screen inside the second one (FR8.10). The Customer Directory lists every Customer holding at least one Assessment, each row condensing what FR8.6 tracks over time to its latest point: name, most recent assessment date in any state, that assessment's rating grade where FR5 has run, and the most recent Approved assessment's locked limit and terms. A customer with no assessment does not appear — FR8.3's New Assessment search is that customer's only route. Selecting a row opens FR8.11's detail view, which assembles rather than reimplements: FR8.6's trend, a list through to FR8.5's drill-down, and FR1.9's documents. Same two capabilities as above, one implementation each, now reached from two entry points. The distinguishing property is intent, and it is enforced, not described: nothing on this surface edits a field, ratio, rating, or document in place, and starting or continuing an assessment stays FR8.3's path (FR8.11).

From v0.10 the surface also carries one route out, and it changes no boundary (FR8.11, PRD v0.10). Refresh this customer takes a user from the detail view into FR8.3's Refresh Assessment flow: the customer is pre-selected always, and the specific assessment is pre-selected as refresh source when the view was reached through FR8.5's drill-down — otherwise FR8.3's default-to-most-recent rule stands unchanged. The action is gated to users holding FR8.3 rights, the boundary FR8.3 already enforces rather than a new permission, so an Auditor or Approver is offered nothing. Both endpoints are this component's own: it serves FR8.11 and it evaluates FR8.3's entry point, so the route is one component connecting two of its surfaces and the pre-selection is a default on a selection step it already owns. The read-only guarantee above survives intact — the route leaves the view, it does not add an edit to it.

FR1.9's document list is served here, and that is the v1.8 boundary call. Per document: type, period where it has one, every version with its upload date and uploader (FR1.5), and every assessment currently referencing it (FR1.6). The first half is Document Intake's data read at view time; the second half is a customer-scoped lookup across the many-to-many relationship that only this component can perform. Serving them from two components would put FR8.11's single role-scope rule in two places (§01 boundary review). This component gains no write path to Document and never has one — opening a document from the list takes no action on any assessment.

Role scoping is applied here, before the query reaches data (NFR Confidentiality/RBAC, FR8.10). An Analyst's directory holds only customers with an Assessment they or their team own, and each row is computed only from the assessments that Analyst can see — so the scope filter runs on the aggregate, not on the list afterward. An Auditor's directory is limited to customers holding at least one completed assessment, consistent with FR9.3. Approver and Admin inherit the existing rule unchanged. Two consequences worth building for: a customer whose assessments are all invisible to the caller must be absent from the list rather than present and blank, and a row's blank rating cell means “FR5 has not run” while a blank limit cell means “no Approved assessment” — two different absences that must not render alike (§07). OPEN — whether the Auditor's scope should widen on this surface (§09).

The two rules that govern a delta are implemented once, here. A differing config_version_id between the two assessments is stated alongside the delta — never presented as like-for-like across a methodology change (FR8.8, FR10.3). A ratio Provisional or Not Calculable on either side gets no delta at all; that comparison renders unavailable with the reason and the side it came from (FR8.8, FR3.8). Where both conditions hold, suppression wins. FR8.9 applies the same two rules to Rating and Recommendation. The rules read the engines' existing stamps, not ratio semantics — and the source assessment is never re-derived to make it comparable, which would rescore a closed assessment and break FR10.3 (§07).

FR11.1–FR11.3 · NFR Traceability

Why FR12 lands in this section, and not in the pipeline or the engines. It advances no document toward a number — nothing it produces is an input to FR4, FR5, or FR6 (FR12.6) — so it fails §04's defining property, and it computes nothing from confirmed fields, so it is not a §05 engine. It exists for the reason the other five components here exist: to make a decision defensible rather than to make it. What it adds is a category this section did not have — evidence gathered from outside the system, as against records of what happened inside it. Hence the section title.

Two components, not one, from v0.6. FR12 needs a roster of natural persons to screen, and until v0.6 FR12.2 assumed one existed with no requirement producing it. FR3.11 now does, and it resolves to its own component (§01 boundary review) — placed here rather than in §04 by what it serves, not by what it looks like. It is a human-review surface, which reads as pipeline shaped, but it advances no document toward a number and feeds no engine; it exists to make FR12's scope defensible, which is this section's defining property.

The screening trigger moved at v0.6, and it moved earlier. FR12.1 previously fired on submission for approval (FR7.2). The independent review found the arithmetic didn't work: FR12.6 makes an FR5.3 qualitative justification the only place a finding can be cited, and FR5.3 is edited before submission — so findings triggered at submission arrived after the only window that could use them, which made FR12.6 unsatisfiable in practice. FR12.1 now fires the moment FR4 ratio computation completes: the earliest point at which an assessment-scoped screening run is meaningful, and the maximum lead time before the analyst reaches FR5.3. Still one event-triggered run per assessment, still no scheduled job. In §03 the trigger edge accordingly leaves the Ratio Engine, not the Approval Workflow.

It gates nothing, deliberately. PRD §2.12 states that no release makes FR5.1–FR5.2 or FR6 depend on FR12. So it runs advisory and asynchronous alongside FR5, FR6, and FR7, and the FR1→FR7 critical path completes whether or not screening has returned — which is why the §03 edge into it is a dotted trigger and the only edge out of it goes to the analyst. The earlier trigger strengthens this rather than weakening it: with FR5 and FR6 still to run, there is more of the path left to complete without waiting. Rejected: block submission until screening completes, on the FR3.10 precedent. The precedent doesn't transfer. FR3.10 blocks on a Provisional result because that is a number already inside the assessment and known to be untrustworthy; an unreturned screening is an absence that bears on no computed value. Blocking would put a Must/MVP workflow behind a Should/V2 feature dependent on live third-party retrieval, handing any provider outage the power to stop credit decisions. FR12.7 handles the real risk instead — that the absence goes unnoticed.

Screening Subject Register & Review

Workflow Should V2

New at v1.5, from PRD v0.6's FR3.11. Holds the customer's roster of natural persons in FR12's screening scope — directors, beneficial owners, guarantors — and the human review that decides which of them are real enough to spend a screening query on. Presents each FR2.8 candidate with the tier that produced it, labelled as the requirement words it: “Found in statement,” “Found in registration document,” or “Manually added.” Accepts Confirm, Amend, and Not Present per entry (FR3.4, FR3.7 pattern), shows a confidence indicator for extracted candidates and none for manual entries, and offers the FR3.3 source jump where a source document exists.

Why it is not part of Field Review, Confirmation & Posting. Same status grammar, opposite scoping rule. Field Review's defining guarantee after v0.6 is that field state never crosses an assessment boundary (FR1.7). ScreeningSubject belongs to Customer and is deliberately shared across every assessment for that customer — never copied, never reset per cycle, because a director is a fact about the entity, not about one assessment cycle. Two entities with inverse scoping invariants in one component is the shape that produces the exact bug FR1.7 was written to fix, run in reverse. Three secondary reasons in §01's boundary review: no recompute to make atomic with, a different completion gate, and a Should/V2 surface that would otherwise sit inside MVP's largest Must component.

Not Present here means something narrower than an empty roster (FR3.11). It asserts a role has no natural person to record — no guarantor on this facility — which is a positive finding an analyst made. An extraction that returned nothing is not that: it is an unreviewed empty state inviting manual entry or an explicit Not Present, and the component must render the two differently. Same discipline as FR12.7's three screening states and FR3.8's Not Calculable: an absence someone confirmed must never look like an absence nobody checked.

Only Confirmed or Amended rows reach the screening agent (FR12.2). Unconfirmed candidates are excluded — a machine-extracted name is not yet trustworthy enough to run an open-web identity search against, and searching one is itself an act of personal-data processing, not a free preview. Not Present rows are excluded for the obvious reason. The consequence to design for: an incomplete roster narrows FR12.2's scope silently, so this component owns making roster completeness visible before a run, in the same way FR3.9 makes field-review completeness visible.

It is a personal-data component before it is a review surface. NFR Personal data — adverse-media subjects makes the point directly: capturing a name into ScreeningSubject is new structured personal-data storage in its own right, whether or not a screening run ever executes. The lawful-basis, retention, and subject-rights questions that gate the FR12 build therefore gate this component too, and they bite here first — this is where the data enters the system (§08, §09).

FR3.11, FR2.8 (consumer), FR12.2 (supplier) · §4 ScreeningSubject · NFR Personal data — adverse-media subjects

Adverse Media Screening Agent

Agent Should V2

Runs once per assessment, triggered immediately after FR4 ratio computation completes (FR12.1, changed at PRD v0.6 — see the callout above), searching the open web for adverse media on the customer entity, its recorded trading names, and every director, UBO, and guarantor standing at Confirmed or Amended in the customer's ScreeningSubject register (FR12.2, FR3.11). Returns adverse media only, in FR12.3's enumerated sense: insolvency filings, litigation, fraud allegations, financial-distress signals, management turmoil or departures, regulatory action, negative press. Records actor, timestamp, and query scope per run, and logs every review-status change on a finding, to the FR9.1 standard (FR12.8). OPEN — no search or news data source is selected, and this plan deliberately names none (§09).

The sanctions/PEP exclusion is architectural, not a scope line. A sanctions hit is a legal determination against a licensed, versioned list, and its compliance value comes entirely from provenance: which list version was screened, on what date, and a contractual completeness guarantee behind it. Open-web search supplies none of those, and a false negative from it means nothing. A component doing both would run licensed-list infrastructure beside a scraper — one output legally load-bearing, the other explicitly not — and surface them under one badge, which is the shortest available path to a user reading “no adverse findings” as “not sanctioned.” Two trust models, two components; this plan proposes only the open-web one. No sanctions or PEP capability is specified anywhere in this document (PRD §0.1, FR12.3).

Output: one AdverseFinding per hit (PRD §4) carrying subject type and name, source URL, headline or snippet, publish date, relevance score, review status, and screening run ID. The source URL is mandatory on every finding, and is the same commitment FR2.2's source-location pointer makes for an extracted field: a claim is usable in this system only if a human can reach what produced it. NFR Traceability then applies unchanged — a finding cited in an FR5.3 justification must stay inspectable at audit years later, which has a consequence the PRD leaves implicit and §07 makes explicit.

The human gate is the same gate this plan already enforces twice. No finding auto-populates a rating or an FR5.3 adjustment; an analyst reviews each and marks it Relevant, Not Relevant, or Needs Follow-up (FR12.5), and only Relevant findings may be cited as evidence (FR12.6). That is FR6.2's shape — a proposal only a human action converts into effect — and FR3.8/FR3.10's shape — machine output never treated as fact until a human has checked it against the source. FR12.5 names the analogy itself. The roster consequence: this component has no write path into any §05 entity. It writes AdverseFinding, and nothing else.

Three states that must never render alike (FR12.7): not yet run, run with no adverse findings, run with findings pending or completed review. A UI and data-model discipline point identical to Provisional-vs-Confirmed, with the same failure mode — a missing badge read as an all-clear. “Clean” is a positive assertion with a run behind it, so screening status is a stored field on the Assessment, not something inferred from whether AdverseFinding rows exist: zero rows cannot tell two of the three states apart.

Not the integration point for paid data. Commercial credit-agency and company-data feeds are a separate future iteration per PRD §2.12 and §5 — not FR12, and not this component by default. Whether such a feed would eventually attach here, to a sibling component, or as structured input to the Ratio/Rating path is an open design question, not a decision made now.

FR12.1–FR12.8 · §4 ScreeningRun, AdverseFinding; reads ScreeningSubject · NFR Untrusted external content; Personal data — adverse-media subjects

07 Cross-cutting guardrails

These apply to every component above, agentic or not:

Validation gate: no component may treat an Unconfirmed field as fact. Resolved in PRD v0.2 — v1.0 of this plan flagged FR3.8 as permitting two incompatible treatments (exclude the field, or compute and flag Provisional) and recommended the second, because exclusion silently changes what a formula measured: a current ratio missing one current-liability line is not a smaller current ratio, it is a wrong one presented cleanly. FR3.8 now mandates Provisional marking, and FR3.10 adds the two consequences that make it bite — submission for approval is blocked while any Provisional result stands, and a Provisional rating never reaches the Recommendation Engine.
A stated non-computation is not a value, and not a Provisional either. New at v1.5, from PRD v0.6's Not Present field status and Ratio.not_calculable_flag. It earns its own entry rather than a clause in the gate above because the ambiguity it replaces did real damage: a line item genuinely absent from an unaudited management account could never leave Unconfirmed, so its ratio stayed Provisional, so FR3.10 blocked submission — permanently, on a field the analyst had already checked. The escape hatch is a third terminal status, and it comes with three rules that must hold everywhere the value is rendered, stored, or consumed.

(1) Never substitute. A Not Calculable ratio stores no value (PRD §4 Ratio.value null). No zero, no partial computation over the inputs that are present, no last-period carry-forward. This is the same argument FR3.8 already makes against excluding an Unconfirmed field — a current ratio computed without one current-liability line is not a smaller current ratio, it is a wrong one presented cleanly — applied to a field that will never arrive.

(2) Never conflate with Provisional. The two are mutually exclusive per ratio and the precedence runs one way: any required input at Not Present makes the ratio Not Calculable regardless of the status of its other inputs; Provisional applies only when every required input exists in the source and at least one is still Unconfirmed. They mean opposite things about what a reviewer should do next — Provisional is resolvable by reviewing further, Not Calculable is finished — and they carry opposite submission consequences under FR3.10. One shared badge, one shared flag, or a UI that renders both as “—” collapses that distinction and hands back the deadlock in a new form.

(3) Never render as a gap. Not Calculable must be visibly distinct from a computed value, from Provisional, and from not-yet-computed. This is the FR12.7 rule — a clean screening run must not render identically to no screening — and the FR3.11 rule about an empty subject roster, in a third place. All three are the same failure: an absence someone confirmed rendering identically to an absence nobody checked. It bites hardest here, because Not Calculable is the only one of the three that passes the submission gate.

OPEN — how FR5.1's scorecard consumes a Not Calculable ratio (exclude and reweight, neutral score, or another treatment) is a methodology question pending the baseline template (§09). Until it is answered the Rating Engine must propagate the state rather than resolve it; coercing it to a number inside the scorecard would defeat rule (1) at the one point where nobody is looking at the ratio directly.
Field state never crosses an assessment boundary. New at v1.5, and a correction to this plan as much as an addition — through v1.4 the plan described a field set as belonging to the document version that produced it, which PRD v0.6's FR1.7 establishes it does not. ExtractedField belongs to Assessment; document_id is provenance only. The rule: no confirm, amend, Not Present, or recompute in one assessment may change what any other assessment shows, even when both cite the same statement, and even when one of them is Approved and closed. Enforced structurally rather than by convention — reuse copies the fields (FR1.7) so there is no shared row to mutate, and every copy resets to Unconfirmed so no assessment inherits a human confirmation made on a different file (§04). This is the guardrail FR8.2's per-field never-overwrite promise and FR4.3's scoped recompute both rest on.

The one entity deliberately exempt is ScreeningSubject, which belongs to Customer and is shared across assessments (§06, §08). The exemption is not an inconsistency: a director is a fact about the entity, not a reading of one statement, and copying the roster per assessment would produce divergent screening scopes for the same customer. Stated explicitly because the natural reflex, once FR1.7 is understood, is to apply copy-on-reuse everywhere.

Reading across the boundary is not crossing it — a distinction v0.7 forces into the open. FR8.5's drill-down, FR8.6's history view, and FR8.8–FR8.9's comparison all read a second assessment's rows. None violates this guardrail, because the guardrail forbids one assessment's activity changing what another shows, and a read changes nothing. The reflex to guard against here runs the opposite way from the one above: treating FR8.8's read as licence to re-derive the source assessment's ratios under the current config so the two sides are “comparable.” That rescores a closed assessment and breaks FR10.3 outright. FR8.8's answer to a config difference is to state it alongside the delta, never to remove it (§06). The PRD makes the same point three times over — FR1.7, FR4.4, FR8.8 — because copy-on-reuse, within-assessment period trend, and cross-assessment comparison are easy to conflate; the companion State Management Plan §07 separates all six cross-boundary paths by what each reads and writes — six from PRD v0.9, which adds FR1.9's document browse as a read across the assessment side of the FR1.6 relationship rather than into any assessment's own rows.
Never silently overwrite: three separate never-overwrite rules that must be implemented as one habit, not three exceptions — document re-upload creates a new version (FR1.5), field amendment retains the original extracted value and confidence (FR3.6), and a Refresh Assessment creates a new linked assessment version rather than editing the last one (FR8.2–FR8.4). Every one of them is paired with an audit entry (FR9.1). PRD v0.6 adds the field-level fourth — FR1.7's copy-on-reuse, which is what makes FR8.2's never-overwrite promise hold below assessment granularity; it is stated separately above because its purpose is isolation, not history.
Segregation of duties: approver ≠ preparing analyst, enforced by the system (FR7.5). FR7.5 now requires enforcement at both submit time and decision time — checking only at submission lets an assessment be routed to a queue the preparer can later claim from. FR7.6 sets block-by-default when no eligible second approver exists (small team, leave, a customer whose only two credit staff both touched the file) and requires any break-glass path to be an audited exception, never a silent bypass. OPEN: the delegation model itself, since the safe default is also the one that stalls the business.
Config immutability for historical results: a methodology change must never retroactively rescore a past assessment (FR10.3). This is the same problem Atlas solved with dated, config-tagged snapshots, and the same solution applies: the Ratio, Rating, and Recommendation engines cannot be “read current data, compute, return” services — each writes an immutable result stamped with the config version that produced it. PRD v0.2 closed the gap v1.0 of this plan found here — config_version_id now sits on Ratio and Recommendation as well as Rating (FR4.5, FR6.4), and FR4.5 states the rule directly: compute on write, not on read. The consequence for retention is in §08: a config version must outlive every assessment computed under it.
Reconstructability, not just lineage: NFR Traceability sets a higher bar than FR4.2 — every rating must be reconstructable from source documents at any later date, which requires four things to survive together for the full retention period: the source document, the field-level source pointer into it, the config version, and the extraction model/prompt version that produced each field. That fourth item was missing from the PRD's data model at v1.0 of this plan — without it an FR2.1 model upgrade makes a past extraction unreproducible even though every stored value is intact. PRD v0.2 added it as FR2.7 and as ExtractedField.extraction_model_version.
The recommendation is a proposal, never an application: nothing downstream of the Recommendation Engine may apply a limit or terms to a live customer account without an FR7.4 approval (FR6.2). FR6.2 now states the downstream half explicitly: no system may act on a proposal that has not reached Approved state. This is the guardrail most at risk from the OPEN ERP/CRM integration in PRD §5 — whichever component eventually writes a limit outward must read Approved state only, and must be the sole path outward.
Role-scoped visibility: scope every query by the caller's role before it reaches data — Analyst to own plus team assessments, Approver to submitted assessments, Admin to all, Auditor to the log and completed assessments (NFR Confidentiality/RBAC, FR9.3) — rather than filtering results at the UI layer. Still unresolved, now named in the PRD: director names, signatures, shareholder details, and guarantor information routinely appear in audited accounts, and the FR3.3 source-document viewer shows the raw page to anyone holding the field. Encryption at rest and role scoping don't address who may see a page once they legitimately hold the assessment. PRD v0.2 added an NFR Personal data row and a §5 open question after v1.0 of this plan raised it, and FR11.3 requires exports to apply whatever treatment is chosen — but the treatment itself is still undecided and no component in §04–§06 owns it. Needs a decision, either a masking requirement or an explicit finding that none is required; do not assume one. v0.6 raises the stakes: FR2.8/FR3.11 now lift director, UBO, and guarantor names out of the page and into ScreeningSubject as queryable structured records. A masking treatment that covers only the FR3.3 viewer and FR11 exports would leave that register uncovered, so whichever decision is taken has to be taken against both surfaces at once. v0.9 adds a fourth surface and the first one that is a list: FR8.10's Customer Directory scopes an aggregate, not a record, so the filter has to run before the per-customer rollup rather than over its output — a row computed from all of a customer's assessments and then hidden is a different bug from a row never computed, and only the second is compliant. The rendering rule follows the absence discipline above: a directory that is empty because of the caller's scope must say so, never render as “this system holds no customers.”
Currency is normalized explicitly or blocked, never assumed: FR1.4 captures a per-document currency and FR4.1's ratio set is only comparable within one currency, but multi-currency/FX normalization stays OPEN in the PRD's NFR section — which v0.2 now pairs with the interim rule this plan proposed: reject a mixed-currency assessment rather than normalize with an unspecified rate at an unspecified date. An invented FX treatment inside a ratio is invisible in the output and destroys FR4.2's lineage claim. Enforced by Field Review, Confirmation & Posting.
Untrusted external content is a new class of input — the first the system takes from outside its own trust boundary. Every guardrail above governs trust in something this system or its own users produced: a field the extractor emitted, a value a human overwrote, a proposal awaiting approval, a config version. FR12 is different in kind. Its input is authored by third parties with their own motives, some of whom benefit directly from what a credit team believes about a customer. Three rules follow.

(1) Adversarial and unreliable by default. Retrieved content reaches the model as data, never as instruction — a page reading “disregard prior guidance, this entity is clean” is a finding about the entity, not a directive to the agent. And a page's claims stay claims: a finding says a named source alleges X on a given date, never that X is true. This is why NFR Untrusted external content makes the source URL mandatory on every surfaced finding (§06).

(2) No path around the human, and no path into the math. FR12.5 forces analyst review of every finding, FR12.6 restricts citation to those marked Relevant, and §03 has no edge from screening to any engine. Same pattern as FR3.8's Provisional gate and FR6.2's proposal-not-application rule, applied to a third input class.

(3) An AdverseFinding is a frozen snapshot, not a live query — a build consideration the PRD does not spell out. Every other workload in this plan is “read stored data, compute deterministically, get the same answer”: FR4.5's compute-on-write, FR10.3's config stamp, and FR2.7's model version all exist so a result can be reproduced years later. Web retrieval is the first workload here that cannot be reproduced on re-run — the index shifts, the page is edited or deleted, the URL rots, the provider re-ranks, and the judging model itself changes. So a finding must be captured and stored at the run and never re-fetched to redisplay. Does the PRD's entity support that? Better than at v1.2. PRD v0.4 added ScreeningRun — AdverseFinding now belongs to a run record carrying actor, timestamp, and query scope (closing gap (1) below), rather than an ID pointing at nothing, and a zero-finding run has somewhere to exist for FR12.7's sake. headline_or_snippet still stores captured content rather than re-fetching it. Two gaps remain, raised in §09: no relevance-model/prompt version on either the run or the finding, the direct analogue of ExtractedField.extraction_model_version, without which a later re-run reaching a different judgement is unexplainable; and no position on whether anything beyond the snippet is retained, which decides whether a cited finding survives its URL rotting — and which collides with the still-OPEN retention question on personal data (§08).

This system is an evidence file, not a task tracker. 10 Build sequence vs. the roadmap

Sequencing follows the MoSCoW/release tags in PRD §2 wherever a component maps to a numbered FR. Two placements are this plan's own inference and flagged as such: the Registry and Audit Log carry Must/MVP FRs but their position — before the pipeline rather than after it — comes from dependency, not from the PRD.

OrderComponentsWhy this order
MVP 1Customer & Assessment Registry, Audit & Access LogFoundations, not a later governance layer. FR9.1 requires extraction confidence scores to be logged, so the log must exist before the component that produces them; FR8.1 requires every assessment to tie to a customer, so nothing upstream has anything to attach to without the registry. Retrofitting an append-only log after mutable writes have shipped means backfilling history that was never captured. This plan's own sequencing call — the PRD tags both Must/MVP but doesn't order them. Carries FR8.3's entry point at v1.6. New-vs-Refresh is a read of the customer's prior-assessment count and a version mint, both of which this row already builds — refresh is core lifecycle, not an add-on, and FR8.3–FR8.6 are Must/MVP. The refresh source link must be in the first migration for the same reason ExtractedField.assessment_id is: retrofitting a link after versions exist means inferring, for every historical assessment, a source that was never recorded (§09). What this row cannot finish is the parts with no downstream to read — FR8.5's drill-down and FR8.6's history have no ratings to show until MVP 5.
MVP 2Document Intake & Versioning → Field Extraction & Validation RoutingNothing downstream has data until these exist, and this is where MVP's only agentic capability sits (§02). Build the extraction evaluation harness here, not later — FR2.2's confidence score is load-bearing for FR2.5's mandatory-review floor and FR3.5's bulk-confirm, so calibration has to be measured, not assumed. FR2.4's thresholds stay tunable config throughout (§09). FR1.7 belongs here, at MVP, not in V2. Copy-on-reuse is a correctness fix to the core pipeline, not an extension: without it the very first re-assessment that reuses a prior-period statement corrupts the assessment that first posted it (§07). It spans both components in this row — Intake raises the reuse event, Extraction writes the copies — so it is built here rather than deferred to MVP 3, and ExtractedField.assessment_id must be in the schema from the first migration, since retrofitting field scope after fields exist means re-deriving ownership for every historical row. v0.7 adds the second trigger for that same event — FR8.4's refresh initiation, where the reuse event is raised from the Registry's reference set rather than from an upload (§03, §04). It is one extra caller of a path this row already builds, so it costs an entry point, not a component.
MVP 3Field Review, Confirmation & PostingFR3 is the core GUI requirement and the largest single block of Must/MVP sub-requirements. Ships before any calculation engine because the FR3.8 gate is the only legitimate path into a ratio — building the engines first invites a temporary bypass that then has to be removed. PRD v0.6 adds three MVP obligations to this row and no new component: the period axis (FR3.1), the third terminal status (FR3.7 Not Present), and review-item counting per field-period cell (FR3.9). All three are Must/MVP because they change the screen's data shape rather than extending it — adding a period axis or a third status after the review UI ships is a rewrite, not an increment.
MVP 4Ratio Engine + the versioned methodology config schema and read path (FR10.1, FR10.3–FR10.5)All of FR4 is Must/MVP, and PRD v0.2 now tags the config schema Must/MVP too — so this pairing is the PRD's own sequencing, not this plan's inference as it was at v1.0. Build the seam rather than hard-coded formulas, so FR10.3 has something to point at from the first computed ratio. Schedule risk: FR4.1's formulas are PLACEHOLDER pending an external deliverable outside the build team's control — build against the seam with a provisional config so the component is testable and only its contents are blocked. Carries two v0.6 additions: not_calculable_flag alongside provisional_flag, mutually exclusive (FR3.8), and the FR12.1 trigger emission on computation complete — a fire-and-forget event with no V2 consumer until FR12 lands, so it costs an event, not a dependency.
MVP 5Rating / Scorecard Engine, Recommendation Engine, and the Registry's read surfaces — cross-assessment read models (FR8.5, FR8.6, FR8.8–FR8.9) and the browse entry point (FR8.10, FR8.11, FR1.9)FR5.1–FR5.2 and all of FR6 are Must/MVP, and both consume the MVP-4 config seam. Same schedule risk as MVP 4, concentrated: these two are the most template-dependent components in the roster, and FR6.1's sizing basis is additionally OPEN on whether it needs non-rating inputs at all (§09) — which is why they are separate components (§05). If the template is still missing at this point, this is the row that slips MVP, so escalate its absence here rather than at MVP 4. The Registry's second appearance is a dependency, not a re-plan. FR8.5, FR8.6, and FR8.8–FR8.9 are all Must/MVP and all read output the engines produce, so none can be built before there is something to read — FR8.8's ratio delta needs the Ratio Engine of MVP 4, and FR8.9's grade movement and limit delta need both engines in this row. They ship here rather than at MVP 1 for that reason alone; the entry-point and version-link half of FR8.3–FR8.4 shipped at MVP 1–2. No engine gains logic in this row on their account: the delta is arithmetic over stored rows, and the two governing rules read stamps the engines already write (§01 boundary review). One sequencing consequence worth stating — FR8.8's two rules are testable only against fixtures that carry a Provisional flag, a Not Calculable flag, and a config-version mismatch, so those cases belong in this row's test set rather than being discovered when the first real refresh crosses a methodology change. The browse entry point joins this row at v1.8, and its placement is a dependency rather than a preference. FR1.9, FR8.10, and FR8.11 are all Must/MVP — read off PRD §2's Release column, not inferred from the FR8 family's tag. FR8.11 assembles FR8.6's trend and FR8.5's drill-down by cross-reference, so it cannot exist before they do; FR8.10's rows carry a rating grade and an approved limit, which need both engines in this row; and FR1.9 has no surface of its own at any release — FR8.11 is the only place it is rendered — so shipping it earlier would ship a capability with nowhere to appear. Two build notes. The directory degrades by design rather than by accident: a customer whose latest assessment has not reached FR5 shows a blank grade, and one with no Approved assessment shows blank limit and terms, so the surface is testable against a partly-populated system and does not need a fully decided customer to render. And its fixtures are role fixtures, not data fixtures — the FR8.10 scope rule is only tested by an Analyst who owns some of a customer's assessments and not others, which is a case no other row in this sequence produces (§07). PRD v0.10's Refresh this customer route ships in this row too — it connects FR8.11, built here, to FR8.3's entry point, built at MVP 1, so it costs a gated link and a pre-selected default, not a component. Its test case is the gate: an Analyst sees the action, an Auditor reaching the same customer does not.
MVP 6Approval WorkflowAll of FR7.1–FR7.5 is Must/MVP. Last of the path components because it has nothing to approve until MVP 5 produces a recommendation, but it carries the segregation-of-duties constraint (FR7.5) that the whole control story rests on — so its open fallback question (§09) needs answering during MVP 5, not during MVP 6.
MVP 7Reporting & ExportFR11.1–FR11.3 are Should/MVP, one of four Should/MVP requirements alongside FR8.7 — not the sole exception it was described as at v1.3, but still the last component in the critical path and the one with the least standing to block a compressed MVP: it has nothing complete to export until MVP 6 closes an assessment, and dropping it loses a deliverable, not a control. Carries the config-version and role-scope constraints in §06.
V2Methodology Config editing surface and change-control gate (FR10.2), qualitative override into the Rating Engine (FR5.3), the screening-subject capture chain (FR1.8 into Document Intake, FR2.8 into Field Extraction, FR3.11 as the new Screening Subject Register & Review), Adverse Media Screening Agent (FR12), multi-approver committee into the Approval Workflow (FR7.7)Matches the PRD's own V2 tags — FR1.8, FR2.8, FR3.11 are all Should/V2, alongside FR12 and FR5.3. FR10's split is explicit in the PRD: schema at MVP 4, editing surface only at V2. FR5.3 and FR7.7 are capability extensions to existing components, and the MVP data model already shapes both — an adjustment layer on Rating, a decision collection on Assessment — so neither needs a migration. Order within V2, now three stages rather than two: (1) FR5.3, (2) the FR1.8→FR2.8→FR3.11 capture chain, (3) FR12. FR5.3 comes first because FR12.6 makes its justification the single sanctioned destination for a reviewed finding, so shipping screening first produces findings with nowhere legitimate to land — and an analyst holding evidence with no place to record it will put it somewhere unsanctioned. The capture chain comes before FR12 for a harder reason than sequencing preference: FR12.2 draws its entire search scope from Confirmed or Amended ScreeningSubject rows, so screening built first has an empty roster and screens the entity only — which is the assumption v0.6 exists to remove. Within the chain, FR2.8 needs FR1.8 for its tier 2, and FR3.11 needs FR2.8 for anything to review, but each degrades rather than blocks: FR2.8 without FR1.8 falls through to manual entry, and FR3.11 with no candidates is a manual-entry surface. FR12.1's new dependency does not reorder anything — the trigger now hangs off FR4, which shipped at MVP 4, so it is satisfied before V2 opens; what changes is the integration surface, from the Approval Workflow to the Ratio Engine (§03). FR12 remains a genuinely new component and the roster's only pure agent (§02), carrying its own evaluation harness, the open questions in §09 of which two block the build outright, and the untrusted-input guardrail in §07 — budget it as a component, not as an extension. The Screening Subject Register is a second new component but a small one: deterministic, no harness, reusing FR3's status grammar — its cost is the personal-data decision it forces, not its code (§06).
V3ERP/CRM write-back of approved limits; portfolio-level views across customers; optionally, a conversational layer over approved assessmentsNone of these has a requirement in PRD v0.10. The write-back is an OPEN question with no owning component (§09) and must read Approved state only (§07). A conversational layer is the Atlas-shaped capability this PRD deliberately does not ask for (§01) — if a future PRD revision requests one it slots in as a read-only consumer of the Ratio, Rating, and Registry components, and would be the roster's second pure agent after FR12's screening agent.
