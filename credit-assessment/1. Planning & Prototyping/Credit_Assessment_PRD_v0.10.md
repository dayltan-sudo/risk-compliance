## 0. Product Summary

An internal tool for a credit/treasury team to assess the creditworthiness of the business's trade customers from uploaded financial statements, and to recommend a credit limit and payment terms. An agentic pipeline extracts standardized financial fields from audited or unaudited statements with confidence scoring; a human reviews and confirms or amends every field against the source document before it feeds any calculation; the system then computes ratios and an internal rating, proposes a limit/terms, and a two-step analyst-then-approver workflow finalizes the decision.

### 0.1 Scope

| In scope | Out of scope |
|---|---|
| Financial-statement upload, extraction, and human field confirmation | Bank/institutional lending underwriting — this tool sizes trade credit only |
| Ratio calculation, internal rating, limit/terms proposal | Automated write-back of approved limits into ERP/CRM (`OPEN`, §5) |
| Two-step analyst→approver decision and audit trail | Credit bureau / external data feeds, sanctions or KYC screening |
| Per-customer assessment history and export | Collections, dunning, overdue tracking, and actual exposure monitoring |
| Open-web adverse-media screening on the customer entity and named directors/UBOs/guarantors (FR12) | Portfolio-level cross-customer analytics (candidate V3) — FR13 answers questions about one assessment or customer at a time, never across customers |
| Read-only conversational Q&A over an assessment's or customer's already-computed data (FR13) | Sanctions and PEP (politically-exposed-person) screening — needs licensed list data with legal guarantees, not open-web scraping; explicitly not covered by FR12 or any other requirement in this document |
| | Any assistant action that writes to, computes, or advances an entity in §4 — FR13 is read-only by requirement (FR13.3), not just by initial scope |

### 0.2 Success measures

| Measure | Why it matters | Target |

Core GUI requirement.

| ID | Requirement | MoSCoW | Release |
|---|---|---|---|
| FR3.1 | Show extracted fields in a structured table/form grouped by statement section, with **each field shown once as a row and its value from every uploaded period shown side by side as columns** (FR1.3, §4 `ExtractedField.period`) — the review unit is the assessment, not a single document; a field is reviewed once per period it has a value in, not once per document uploaded. `PLACEHOLDER` generic grouping pending baseline template. | Must | MVP |
| FR3.2 | Each field shows a color-coded confidence indicator per FR2.4's bands. | Must | MVP |
| FR3.3 | Selecting a field opens/highlights its exact location in a side-by-side source document viewer. | Must | MVP |
| FR3.4 | User can Confirm (accept as-is) or Amend (edit value) each field individually. | Must | MVP |
| FR3.5 | Bulk-confirm action for all High-confidence fields at once. Confidence is scored per field-period value independently (FR2.2, §4 `ExtractedField`), so bulk-confirm acts on every individual field-period item at or above the High threshold (FR2.4), across all periods — not on a field as a whole. A field High in one period and Medium in another has only its High period-value bulk-confirmed; the other stays for individual review. | Must | MVP |
| FR3.6 | Amending a field requires the new value and an optional reason/comment; the original extracted value and confidence are retained for audit. | Must | MVP |
| FR3.7 | Field status lifecycle: Unconfirmed → Confirmed \| Amended \| **Not Present**. Not Present declares a field genuinely absent from the source document — the analyst has checked and confirmed there is nothing to confirm, not merely left it unreviewed. Like Confirmed and Amended it is a terminal, reviewed state; unlike them it carries no value for Ratio to consume (FR3.8). | Must | MVP |
| FR3.8 | Compute ratios on Unconfirmed inputs but mark every affected result **Provisional** — never silently exclude the field. Excluding an input changes what the formula measured and presents a wrong figure cleanly; flagging keeps it visibly untrustworthy. Where a required input is **Not Present** (FR3.7) rather than Unconfirmed, the ratio has no value to compute at all — render it **Not Calculable**, not Provisional, and never substitute a zero or a partial computation. Provisional and Not Calculable are mutually exclusive per ratio: if any required input is Not Present, the ratio is Not Calculable regardless of the status of its other inputs; only when every required input exists in the source (Unconfirmed, Confirmed, or Amended) does the Provisional rule apply. | Must | MVP |
| FR3.9 | Show a completion/progress indicator counting **review items**, not fields — one item per field-period combination on the review screen (FR3.1), e.g. 34 fields × 3 periods = 102 review items. An item counts as reviewed once it reaches Confirmed, Amended, or Not Present (FR3.7) — Not Present is a completed review outcome, not a gap; only Unconfirmed items count as outstanding. | Must | MVP |
| FR3.10 | Block submission for approval (FR7.2) while any **Provisional** result remains, and never pass a Provisional rating to the Recommendation Engine (FR6). A **Not Calculable** result (FR3.8) does not block submission and does not itself block FR5/FR6 — it reflects a field the analyst has affirmatively confirmed absent, a completed review outcome, not one still pending. Provisional means "resolvable by reviewing further"; Not Calculable means "confirmed absent, nothing left to resolve." `OPEN` — how FR5's scorecard treats a Not Calculable ratio as scorecard input (exclude and reweight, substitute a neutral score, or another treatment) is a methodology question pending the baseline template (§5), on the same standing as FR5.1's other `PLACEHOLDER` items; it does not affect the submission-gate rule stated here. | Must | MVP |
| FR3.11 | Screening subjects (`ScreeningSubject`, §4) follow the same review pattern as financial fields, scaled to identity data: a Confirm/Amend/Not Present action per entry (FR3.4, FR3.7), a confidence indicator for extracted candidates (blank/not applicable for manual entries, FR3.2), and a source-location jump to the statement or registration document where available (FR3.3). FR12.2's search scope draws only from Confirmed or Amended `ScreeningSubject` rows — Unconfirmed candidates are not yet trustworthy enough to spend a screening query on, and Not Present rows are correctly excluded. | Should | V2 |

### 2.12 FR12 — Adverse News & Reputational Screening

Screens the open web for adverse media on the customer entity and named individuals connected to an assessment. Findings are evidence for the analyst's FR5.3 qualitative adjustment, not an automatic score input — ships alongside FR5.3 in V2 for that reason. Sanctions and PEP screening are explicitly **out of scope**: they require licensed list data with legal guarantees, not open-web scraping, and this document does not propose a sanctions/PEP capability anywhere. Paid data sources from credit rating agencies (e.g. commercial company-data or credit-bureau APIs) are a separate future iteration, not FR12 — FR12 covers open-web search only. Two changes in v0.6: the screening trigger moved from FR7.2 submission to immediately after FR4 completes, so findings exist before the FR5.3 window they're meant to feed (FR12.1; 2026-07-30 review, B8); and the screened individuals now have a defined source — the customer's `ScreeningSubject` roster (§4), captured via FR1.8/FR2.8/FR3.11 rather than assumed (FR12.2; same review, B7).

### 2.13 FR13 — Assistant / Conversational Q&A

Read-only conversational Q&A over an assessment's or customer's already-computed and already-confirmed data — ratios and their lineage, rating drivers, assessment/approval status, proposed or approved limit and terms, the FR8.8–FR8.9 cross-assessment comparison, and, once FR12 ships, its screening status and Relevant findings (FR13.10). Not an orchestrator: it holds no write path to any entity in §4 and cannot itself confirm a field, compute a ratio or rating, or advance an approval — every factual answer is a citation to a stored record, never a decision, and grounded through a fixed set of parameterized queries rather than free-text search (FR13.11), so a citation is verifiable by construction. Modelled in the companion architecture plan as a planned sixth agent (`Credit_Assessment_Agent_Architecture_Plan.html` §02, §10) and the roster's second pure agent after FR12 — the only agentic surface that reads the core decisioning entities (Ratio, Rating, Recommendation) rather than the adverse-media periphery, which is why its read scope and refusal behaviour are specified as precisely as FR12's screening scope is. **v0.9 data-model check:** FR1.9 (document browsing) and FR8.10–FR8.11 (Customer Directory) need no new entity or attribute — purely a new read/UI surface over entities already modeled. The Customer Directory list (FR8.10) reads `Customer.name`, `Assessment.created_at`/`state` (for the most recent row per customer), `Rating.band/grade`, and `Recommendation.proposed_limit`/`proposed_terms` (filtered to the most recent Assessment with `state = Approved`), aggregated per customer at query time. The customer detail view (FR8.11) is a new arrangement of FR8.5's, FR8.6's, and FR1.9's read paths over `ExtractedField`, `Ratio`, `Rating`, `Recommendation`, and `Document` — no field on any entity changes, and neither FR8.5 nor FR8.6 is reimplemented. FR1.9 reads `Document`'s existing version chain (`id`/`version`/`upload_date`/`uploader`, FR1.5) and its existing many-to-many reference to `Assessment` (FR1.6) — both already modeled; no join table beyond what FR1.6 already implies is needed.

**v0.11 data-model check:** FR13 (Assistant / Conversational Q&A) needs no new entity. Its read path is `Ratio`, `Rating`, `Recommendation`, `Assessment`, `ApprovalDecision`, `Customer`, and `ScorecardConfig` (for the `config_version_id` a cited figure carries) — all already modeled, all already read by an existing component (the Registry's FR8.5/FR8.6/FR8.8–FR8.9 surfaces, the engines that write them). FR13.9's audit requirement writes `AuditLogEntry` rows exactly as every other read-then-log path does — `entity_type`/`entity_id` per record read, `actor`, `timestamp`; `before_value`/`after_value` are null, since a read changes nothing to record a before/after of. No entity gains a write path it did not already have, and none needs one: FR13 is the first requirement in this document whose entire data-model footprint is reads.

**v0.12 data-model check:** FR13.10 extends the read path to `ScreeningRun` and `AdverseFinding` — both already modeled for FR12, both already read-only from FR13's perspective. No new entity, no new attribute, no new join: FR13.10 filters `AdverseFinding.review_status = Relevant` and reads `ScreeningRun.finding_count` for the not-yet-run/clean/has-findings distinction FR12.7 already defines, exactly as the screening panel itself would. FR13.11 needs no data-model change at all — it constrains *how* FR13 queries the entities above (fixed parameters, no free-text search surface), not which entities it touches.

## 6. Glossary

| Term | Definition |
|---|---|
| DSCR | Debt Service Coverage Ratio — cash flow available to cover debt obligations. |
| Gearing | A leverage measure of debt relative to equity or capital. |
| DSO / DPO / DIO | Days Sales/Payable/Inventory Outstanding — efficiency measures of receivables, payables, and inventory turnover in days. |
| ROE / ROA | Return on Equity / Return on Assets — profitability relative to equity or total assets. |
| Confidence score | Extraction-model certainty (0–100%) that an extracted field value is correct. |
| Provisional | A ratio or rating computed using at least one Unconfirmed field (FR3.8) — blocks submission for approval. Distinct from Not Calculable: Provisional means the input still exists and can be resolved by reviewing further. |
| Not Present | A field status confirming the source document does not contain this line item at all (FR3.7) — distinct from Unconfirmed (not yet reviewed). Terminal and reviewed, like Confirmed/Amended. |
| Not Calculable | A ratio state when a required input is Not Present (FR3.8) — the ratio has no computable value. Distinct from Provisional: does not block submission (FR3.10). |
| Lineage | The chain from a computed value back to the exact source field(s), document(s), and location(s) that produced it. |
| Adverse media | Negative open-web press or public-record content about a screened subject — insolvency, litigation, fraud allegations, financial distress, management turmoil, or regulatory action. Distinct from sanctions/PEP screening, which FR12 excludes. |
| UBO | Ultimate Beneficial Owner — the individual(s) who ultimately own or control a customer entity, as distinct from its directors. |
