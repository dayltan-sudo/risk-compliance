The reading applied to FR8.3, stated once here. FR8.3 defines New Assessment against “an existing Customer with no prior Assessment, or… a new Customer record,” and Refresh Assessment against “a Customer with one or more existing Assessments.” The two conditions are exhaustive and mutually exclusive on prior-assessment count, so the entry point is determined by the customer's record, not chosen by the analyst — there is no path in FR8.3 to an unlinked version 1 for a customer who already has assessments. §03 models it that way. The residual case — an analyst deliberately wanting a clean-slate assessment with no refresh source for an existing customer — has no requirement behind it and needs none for MVP: FR8.3's optional historical-depth clause already covers widening a refresh's period set, and the refresh link is what FR8.8–FR8.9 need to exist at all. No component boundary moves under either reading.

03 Three top-level modes & the assessment entry point

PRD v0.9 makes the system's shape explicit: three ways in, not two. Prepare an assessment (FR8.3), approve one (FR7), or browse what has already happened (FR8.10). The first two write; the third never does.

Three ways in

Browse History is a mode, not a screen inside assessment preparation. FR8.10 says so in its own text — “a third top-level way into the system alongside FR8.3… and FR7” — and defines it by the absence of intent: browsing historical activity “with no intent to create or continue” an assessment. That is a state-model claim, not a UI preference, and it has three consequences this document has to carry. (1) No assessment is in scope. Every state in §04–§06 presupposes an assessment that exists and is being worked on; browse presupposes none, and the user may leave without one ever existing. Modelling it as a Draft substate would be false on its face. (2) It is entered by roles that cannot reach the other two modes. An Auditor has no FR8.3 rights and no FR7 rights, so browse is the only mode that role has — which makes it a peer of the other two by necessity, not just by the PRD's wording. (3) It writes nothing itself. FR8.11 has no in-place edit of any field, ratio, rating, or document, so no state inside this mode mutates anything. PRD v0.10's Refresh this customer does not weaken that: it is a transition out of the mode, and the Assessment it leads to is minted in Prepare mode by the Registry (§05), on the far side of the arrow. A user who stays in Browse mode leaves it exactly as they found it.

The three modes are peers and are entered independently — there is no home state a user must pass through between them, only one they start from. Prepare and Approve are the two that write; the only transition between any pair of modes is the browse-to-prepare arrow, permanent and role-gated since PRD v0.10 (FR8.11). It carries a customer selection, and where the user drilled into one past assessment (FR8.5) a refresh-source selection too — the create itself still happens in Prepare mode under FR8.3's rules. The Approve mode's own states are the Submitted-onward half of §04's machine and are not restated here.
Role-scoped state variation is new to this document, and the convention chosen is stated rather than assumed. Through v1.1 no state in this model varied by who was looking at it. FR8.10's list does: an Analyst sees customers with an assessment they or their team own, an Auditor sees customers with at least one completed assessment, Approver and Admin inherit the existing NFR rule. The convention: role scopes the query, it does not fork the state machine. Browse History is one mode with one set of states for every role; what differs is the row set those states are computed over, which NFR Confidentiality/RBAC already requires be applied before the query reaches data rather than as a filter over its output. Modelling a machine per role would draw the same four states three times and put a security rule in a diagram that cannot enforce it. The one genuine branch, and why it is a branch: the Auditor's scope is an unresolved product question, not a parameter with a known value (§10 branch C), and it is modelled there with the other open questions.
Two kinds of role dependence, and they are not one convention. PRD v0.10's Refresh this customer gate is role-dependent, but not in the way FR8.10–FR8.11's RBAC is, and collapsing them would lose the distinction the PRD itself draws.

Data-scoping gate (FR8.10–FR8.11, NFR Confidentiality/RBAC): governs what rows are visible. Applied inside the query, before it reaches data. Every role sees the same states over a different row set — the convention above.

Action-availability gate (FR8.11's Refresh this customer): governs what may be done with what is already visible. Two users can hold identical browse scope and see the same customer, and only the one with FR8.3 rights is offered the transition. It cannot be expressed as a query parameter, because there is no row to filter — the object of the rule is an outgoing transition, not a record.

What they share, and where the shared part stops: both read the role, neither forks the state machine. Browse History still has one set of states for every role; the Auditor simply has no arrow leaving it. The consequence to build for: a role gate on a transition is enforced where the transition is served (the Registry, §08), not where the data is fetched — so passing the RBAC scope test says nothing about whether the action gate holds, and the two need separate tests. An Auditor correctly scoped to completed assessments who is nonetheless offered Refresh this customer is an access defect that no data-scope check would catch (§09).

FR1.9 needs no entity that does not already exist, and the diagram is the check. Both of its reads resolve against structures modelled since PRD v0.2: the version chain is Document.version plus upload_date and uploader (FR1.5), and the referencing-assessment list is the FR1.6 many-to-many relationship read from the assessment side. No join table beyond what FR1.6 already implies, no new attribute, and nothing on Document that browsing would have to set. This matches PRD §4's own v0.9 conclusion — recorded here as verified against the read paths rather than carried over, because this plan raised the opposite finding against v0.7 and the check is not a formality (§09). The property that makes it safe is that Document is immutable once stored (architecture plan §08): there is no state on it for a read-only surface to fall out of date with.
Browse to Refresh — the one transition out of this mode, confirmed at PRD v0.10. FR8.11's Refresh this customer takes a user from the customer detail view into FR8.3's Refresh Assessment flow. Four properties define it, and they are the whole rule.

(1) It is gated to FR8.3 rights holders. The same boundary FR8.3 already enforces, not a new permission — a role with no legitimate path into FR8.3 by any route (Auditor, Approver) is offered no action at all. An action gate, not a data gate (callout above).

(2) The customer is always pre-selected. FR8.3's search step is satisfied by a default rather than skipped, so the Registry still evaluates the entry-point condition exactly as it does on a direct entry — a user arriving from Browse is offered Refresh because the customer has priors, which is the only reason anyone is (§03 below).

(3) The refresh source is pre-selected only when the view was reached through FR8.5. Drilling into one specific past assessment carries that assessment across as the refresh source; viewing at customer level carries nothing, and FR8.3's default-to-most-recent rule applies unchanged. One conditional default on a step that exists either way — no second selection mechanism.

(4) The mode change must be visible. The user crosses from a surface that writes nothing to one that mints an Assessment on entry (§05). Pre-selection reduces the steps between browsing and a Draft, which is exactly why the boundary has to be explicit — a browse session must not end with a Draft the user did not know they created (§09).

No component boundary moves and no state is stored. The Registry serves both endpoints (§08), and the top-level mode remains a navigation position, not a field — nothing records which mode an assessment was started from, and nothing needs to (§02).

04 Assessment lifecycle, both paths

One state machine, not two. FR8.3's two entry paths differ only in how the Draft's field scope is populated, and that difference is spent before the first review action.

Approved and Rejected are terminal (FR7.4). Returned for Revision is not — it re-enters Draft, so a single assessment may traverse the Draft substates repeatedly and accumulates one ApprovalDecision per approver action. The comparison substate is reachable only on the refresh path and is read-only: entering or leaving it writes nothing (§06).
Two properties of this machine that FR8.3 does not change. A refresh version is an ordinary assessment in every respect after initialisation — same submission gate (FR3.10), same segregation of duties (FR7.5), same never-overwrite guarantee (FR8.2). And the refresh source assessment is not a participant in this machine: it has its own, already-terminal state, and nothing in the new assessment's lifecycle transitions it. That is the structural form of FR8.8's “touches neither assessment's fields or confirmation state” — the source appears in §06's sequence as a read target, and appears in no diagram here as a state holder.

Steps 4–7 and steps 8–10 are independent and may interleave; step 2 precedes both. Nothing in this sequence reads or writes the refresh source assessment's own ExtractedField, Ratio, Rating, or Recommendation rows — the copy sources from the Document's most recent extraction (FR1.7), not from the source assessment's field set.
The window between step 2 and step 7 is a real state, and it must render as one. An assessment exists, in Draft, with a source link and an empty or partial field scope. An analyst who reaches the review screen inside that window sees an empty grid, which is indistinguishable from “this refresh inherited nothing” unless the initialising state is shown. Same discipline the architecture plan's §07 applies three times over — an absence in progress must never render as an absence that is final. Failure handling in §09.
Why the Registry initiates the reference attach rather than writing the copy itself. The architecture plan already fixes two ownerships that this sequence must not disturb: Document Intake attaches document references and raises the reuse event, and Field Extraction is the single component that mints an ExtractedField row (architecture plan §04, §08). Refresh introduces the first case where a reuse event is raised with no upload behind it, so the Registry supplies the reference set. It does not become a second writer of fields — splitting that ownership is the thing the architecture plan's boundary tests reject in three separate places.

The two rules stack; they do not override each other. A differing config version annotates a delta that is still shown (FR8.8 rule 1). A Provisional or Not Calculable input suppresses the delta outright (FR8.8 rule 2). Where both hold, suppression wins and the reason is the flag, not the config — there is nothing to annotate once there is no delta. Implementing them as one combined check produces the wrong output in exactly that case.
What the Registry needs to know about a ratio, and what it deliberately does not. Rules 1 and 2 read provisional_flag, not_calculable_flag, and config_version_id — three stamps the engines already wrote. None requires ratio semantics, so the Registry needs no formula knowledge to apply them. FR8.9's rating-grade movement is the one place ordering matters: grade order is the band sequence held in ScorecardConfig (FR10.1), read as data. The Registry becomes a fourth reader of the config seam, not a writer — and where the two assessments' config versions differ, FR8.8 rule 1 fires and the movement is stated as prior grade to new grade under a declared methodology change, never asserted as an improvement or a deterioration. The one condition that would reopen the ownership call: a future requirement asking the comparison to judge a ratio delta as favourable or adverse. That is methodology, belongs in ScorecardConfig, and would still be read rather than computed by the Registry — but it is the point at which “a delta is arithmetic” stops being true, and it should be re-tested against the architecture plan's boundary criteria if it arrives.

07 Six paths that cross an assessment boundary

The PRD states the FR1.7-versus-FR8.8 distinction three times (FR1.7, FR4.4, FR8.8) because conflating them is the obvious mistake. The invariant that makes all six safe is one rule, not six. The architecture plan's §07 states it: field state never crosses an assessment boundary. Only the first path writes at all, and it writes into the new assessment's own scope from a document — never from, and never into, another assessment's rows. The other five read. Reading another assessment's already-written rows does not cross that boundary in the sense the guardrail means: the guardrail forbids one assessment's activity changing what another shows, and a read changes nothing. The failure mode to guard against here is the reverse reflex — treating FR8.8's read as licence to re-derive the source assessment's ratios under the current config so the two are “comparable.” That would rescore a closed assessment and break FR10.3. FR8.8's answer is to state the config difference instead, never to remove it (§06).
