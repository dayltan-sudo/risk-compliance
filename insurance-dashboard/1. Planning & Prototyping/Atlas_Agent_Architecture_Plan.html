01 Summary of the approach

The prototype already implies the shape of this system: a persistent chat panel with page-aware suggested prompts (promptsByPage, Atlas_App_UI v0.5.html:1678) that currently answers from a hard-coded lookup (chatExactReplies, :1734), and a page-scoped Action Items rail (actionItems, :1640) that is likewise static. The PRD specifies what both should become: a conversational assistant that answers only from live Atlas data and is fully traceable (FR8.3–FR8.4), fed by a document pipeline that turns broker/policy paperwork into validated records (FR3, §9), a ratio engine (FR2), a risk score (FR4, §10), and three newer registers — Contract Requirements (FR7), Insurance Exclusions (FR9), and RiskScanner (FR6).

That maps onto one orchestrator that owns intent-routing, access control, alerting, and answer composition, plus four subagents it queries or that feed it: a document-ingestion & extraction pipeline, a bundle of three computation engines plus the config governance that gates them, a reporting-and-audit pair, and a standalone news-intelligence agent. §03 lays out exactly how those four subagents were arrived at and shows the full diagram; §04–08 give each one its own section, broken into the workflows/functions folded into it. Not all of these functions are “agents” in the sense of something that reasons over ambiguous input — see §02.

Consolidation review (v1.1, historical): the first pass over-separated several steps that were pipeline hops, not decision points. Three genuine merges brought the roster from 19 functions to 12: the ingestion pipeline — PRD §9's seven stages, plus an eighth “Manual Questionnaire” item this plan's own v1.0 draft added on top — collapsed to three, Contract Requirements and Exclusion Conflict merged into one Contract Compliance Engine since the exclusion check is an override on the requirement's own status rather than an independent register, and the Document/Validation Status function folded into the ingestion pipeline instead of standing alone. That 12-function roster is still exactly right at the functional level (§02) — what changed later (v1.6/v1.7, §03) is purely how those 12 functions are packaged into deployable files.

02 Agent vs. workflow — what actually needs an LLM

Every function in §01 got called an “agent” in the first pass of this plan. Most of them aren't — they're deterministic pipelines that happen to be triggered by one. Worth separating cleanly, because the two categories have different engineering needs: agents need prompt design, evaluation, and human-in-the-loop guardrails; workflows just need to be correct and fast. This classification is a property of the function, not of which file it ships in — §03 shows the packaging.

The test: does this function have to exercise judgement over ambiguous or unstructured input — infer intent, choose between options, interpret free text — or is it a fixed sequence of steps with one correct answer given the input? The second kind doesn't need an LLM in the loop at all, and for several of these functions (the ratio and risk-score engines especially) that's a feature, not a gap: FR2.4 requires exact, reproducible calculation lineage, which is an argument against putting a non-deterministic model anywhere near the math.

03 System architecture: 1 orchestrator + 4 subagents

The 12 functions in §02 are still the right functional boundaries. What this section fixes is packaging: instead of 12 separate documents (3 in an agents folder, 9 in a workflows folder), the deployable roster is now 1 orchestrator + 4 subagents — 5 files total, all in one agents folder. A standalone workflows tier stopped earning its keep once every one of the 9 deterministic functions turned out to sit immediately upstream, downstream, or dependency-adjacent to an existing agent, or to another workflow it shares a trigger with. The rest of this plan (§04–08) is organised by this same roster, one section per deployable, with each subagent's absorbed workflows shown as its own numbered level-2 subsection — exactly matching how the specs themselves are written in 2. Agents & Workflows/a. Agents/.

Two kinds of merge, not one: three functions (Intake & Classification, Enrichment & Posting, Alerts & Notification) folded directly into an existing agent because they are that agent's own entry stage, exit stage, or a second delivery surface for logic the agent already computes (Action Items rail and Alerts evaluate the same §12.1 trigger table — running that evaluation twice, in two components, was a duplicate-computation risk with no upside). The other six (the three engines, Config Change-Control, Reporting & Export, Audit & Access Log) had no natural agent host, so they consolidated into two new deterministic-only subagents instead, grouped by shared dependency: the three engines share one config-version dependency and one snapshot-writing discipline, so Config Change-Control — which exists solely to gate that dependency — joined them as Subagent 2; Reporting & Export and Audit & Access Log share the fact that one of Reporting's four outputs is a direct read of Audit's own log, so they became Subagent 3.

04 The orchestrator

Owns the always-on assistant panel (§6.8, FR8), the page-scoped Action Items rail (FR1.5), and — as of rev 1.6 — alert dispatch. It never edits data — it is a read path only.

04.1 Core orchestration

Atlas Orchestrator

Agent Must MVP

Intent + page-context routing — the prototype already scopes suggested prompts and Action Items by the page in view (currentPage, :1657; promptsByPage, :1678); the orchestrator formalises this by using page context as a prior on top of NL intent classification, so “which sites are under-insured” asked from Coverage Adequacy and from Global Map can route to the same Coverage & Ratio Engine (§06.1) with different default framing.

Access-scope gate — every query is filtered through the caller’s role and entity/site scope (§4.2) before it reaches a subagent, so an Entity Risk Champion never receives an answer outside their assigned entity.

Answer composition with citations — every answer must trace back to the KPI, policy, or requirement record it came from (FR8.4). This replaces the prototype's static chatExactReplies strings (:1734) with live lookups plus a citation.

Explicit fallback — when no subagent can answer, say so rather than guess (FR8.5) — the prototype's botReplyFor fallback string (:1780) is the right instinct and should carry forward verbatim as a behaviour, not just a copy string.

Hard constraint — decision-support only. No orchestrator path writes to a policy, coverage, requirement, or exclusion record; only Subagent 1 (§05) and a human validator can do that.

PRD §6.8, FR8.1–FR8.5 · Prototype :1678–1798

Reclassified in PRD v0.8: FR8.3–FR8.5 (answering from live data, source-tracing, and free-text fallback) moved from Should/Must-V2 to Must/MVP — the drafting split between “ship the panel” and “ship the answers” was a PRD sequencing artifact, not an intended product cut. The orchestrator now ships answering from live data at MVP, not just routing to page-relevant prompts. That makes it the one MVP-critical agentic capability outside document extraction (§05) — it needs prompt design, an evaluation harness, and tested human-fallback behaviour (FR8.5) built and proven before go-live, not deferred to a later release.

04.2 Alerts & Notification Workflow Must*

Absorbed workflow — shares the orchestrator's own trigger-evaluation step with the Action Items rail (§03) rather than running as an independent component.

Evaluates the §12.1 trigger table — renewal due, coverage gap, low-confidence extraction, carrier downgrade, aggregate erosion, new hotspot, emerging-risk breach, contractual gap, exclusion conflict — and routes to the right recipient over the right channel (in-app, email, Teams). *§12.1's trigger table itself carries no per-row MoSCoW/release tags; only the contractual-gap (FR7.5) and exclusion-conflict (FR9.5) triggers are directly traceable to a Must/MVP requirement, and the emerging-risk trigger's appetite-breach content depends on FR6.5 (Subagent 4's Stretch/V2 tier, §08) even though Subagent 4 itself now ships at MVP. This function is MVP-relevant from day one, but not every trigger it evaluates ships at MVP — see §11.

§12.1–12.2

05 Subagent 1 — Insurance DocAnalyst Hybrid

The literal “analyse documents and extract key information” pipeline — PRD §9's seven stages plus the manual fallback in FR3.9, three level-2 workflows in one file. Only 05.2's extraction step is actually agentic (§02). None post to the live database on their own; every path ends at a human validator.

Consolidated from 8 functions to 3, then packaged as 1 file: the branching that exists (pass a document through, or fork it into the exception queue on failed classification/extraction, per §9.1) happens within a function's own confidence-threshold logic, not between deployable services — so most of the original stage-by-stage boundaries (Intake, Classification, Extraction, Validation Routing, Manual Questionnaire, Enrichment, Posting & Versioning, Recalculation) were hops, not independent decision points. Enrichment, Posting, and Recalculation in particular must fire together for every record with no exceptions (FR2.3 requires recalculation to follow a data change automatically) — splitting them risked a posted record whose KPIs silently failed to refresh if a message between components were lost.

05.1 Intake & Classification Workflow

Accepts single/bulk uploads of PDF, scanned image, Word, and Excel documents; virus-scans, stores immutably, assigns an ingestion ID; detects document type across ten classes — six policy-side (slip, wording, schedule, endorsement, debit note, renewal) and, as of rev 1.6, four contract-requirement classes (customer contract, JV partner contract, lender agreement, government concession agreement) — to select the right extraction model. Both original stages are mechanical, with no reasoning boundary between them.

§9 St.1–2, FR3.1, FR3.2

05.2 Insurance DocAnalyst (core) Hybrid

The agentic half: OCR/NLP/IDP extraction of the §8.2 field set (confidence score + source pointer per field, so every stored value can be traced back to its exact location in the source document per FR3.6) — genuine document understanding over inconsistent broker formats, now also covering the rev-1.6 contract-requirement field set for the four classes in 05.1. The workflow half bolted on afterward: pre-accept high-confidence fields, route the rest to the human review queue with a reason code and owner (the Document Inbox in the prototype, :749–771) — a fixed threshold rule, not a decision. Also the entry point for the no-source-document questionnaire path (FR3.9, prototype modal, :845–900, openQuestionnaire() :1512) — FR3.9 requires manual entries to hit the same validation and audit trail as extracted ones. Re-running a document after model improvements (FR3.8, Could/V2) re-enters here, producing a new version without losing history (§9.1).

FR3.3, FR3.4, FR3.6, FR3.8, FR3.9, §9.1

05.3 Enrichment & Posting Workflow

Normalises currency (dated FX), geocodes sites, attaches carrier credit rating and country-risk index, maps to entity/site master; writes the validated record — preserving the source-document link and field-level location pointer captured at extraction (FR3.6) — versions any change (never silently overwrites — audit entry every time); triggers recalculation in Subagent 2 (§06). External calls (FX, geocode, carrier rating) are retried/cached internally — that's the flakiest part of the chain — but a record is only posted once enrichment succeeds; this component never posts an un-enriched record to avoid blocking. The rev-1.6 contract-requirement path (05.1’s four new classes) bypasses this stage entirely — a required-limit figure needs none of Enrichment's three external calls, so it posts directly to its own register instead (see Insurance DocAnalyst.md §11a).

§9 St.5–7, FR3.6, FR3.7, FR2.2, FR2.3, FR3.5

Note on data migration: back-book policies load through this exact same pipeline — there is deliberately no shortcut bypassing human validation for historical records (§9.2). The pipeline is designed once and reused for both new intake and migration, sequenced by entity/BU. Two migration-specific rules it needs to enforce, not just the ordinary validation gate: a migrated record must clear the same completeness floor as the Data Completeness & Confidence KPI (§7.6) before it's treated as “live” — records below the floor stay in the exception queue rather than being silently included — and each entity runs Atlas in parallel with its existing local tracker for at least one renewal cycle before that tracker is retired, to catch migration gaps (§9.2).

06 Subagent 2 — CoverageAnalyst Deterministic

What the orchestrator actually queries to answer a coverage, risk, or compliance question, plus the governance workflow that gates all three. Each of the three engines owns one register from the data model (§8.1) and is the single place that register's business logic lives; none of the four functions below need an LLM.

Merged (historical, v1.1): Contract Requirements and Exclusion Conflict are one Contract Compliance Engine (06.3) because §6.9 describes one status decision (Met / At-risk / Gap / Excluded), not two independent registers that happen to interact — the exclusion check is an override on the requirement check. As two separate functions this needs strict ordering and a tie-break rule for disagreement; as one function with one status field, that race condition doesn't exist. The Document/Validation Status function is also gone from this tier — it never owned a register, it read the ingestion pipeline's own queue state, so the orchestrator queries Subagent 1 (§05) directly instead of through a second, potentially-stale copy.
Packaged, rev 1.6: 06.1–06.3 share one config-version dependency and one Snapshot Convergence discipline (§10); 06.4 (Config Change-Control) exists solely to gate that dependency and computes nothing itself, so packaging it apart from what it gates was the artificial boundary — it joined this subagent rather than Subagent 3, even though both look like “governance.”

06.1 Coverage & Ratio Engine Workflow MVP

Computes ITV, Limit-to-PML, Coverage Gap%, BI Adequacy, RoL, TCOR, Loss Ratio, Claims Frequency/Severity, Carrier Concentration/Credit Quality, Mandatory Cover Compliance %, etc. on FX-normalised values, with full input/formula/timestamp lineage — and writes an immutable, dated snapshot of every value it computes, not just the current figure (§10). Kept as a separate level-2 function from Risk Scoring (06.2) below despite feeding it most of its drivers — a further merge would pull nat-cat, political-risk, and news dependencies (genuinely external to this engine) into what is otherwise a clean financial-ratio calculator.

FR2

06.2 Risk Scoring Engine Workflow MVP

Weighted blend of 8 drivers (§10, PRD) — five of which (coverage gap severity, uninsured TIV, adverse claims history, carrier credit quality & concentration, mandatory-cover non-compliance) are already KPIs 06.1 computes; only nat-cat exposure, political/country risk, and the news-driven signal (from Subagent 4, §08) are genuinely external, separately-sourced indices with their own refresh cadence. Explains every score's driver breakdown; recomputes automatically on underlying data change (MVP) — recomputing on a weight change is a separate, V2 capability (FR4.5). Every recompute writes a dated snapshot tagged to the weight-configuration version that produced it, so a later reweight never rewrites what a score was.

FR4, §10

06.3 Contract Compliance Engine Workflow MVP

Requirements + exclusions, one merged register.

Compares required vs. placed limit per counterparty (customer/tenant, lender, JV partner, government/concession), then applies the exclusion cross-check as an override, producing one status: Met / At-risk / Gap / Excluded (FR7.1–FR7.5, FR9.1–FR9.3, FR9.5–FR9.6, all Must/MVP), each status change versioned rather than overwritten. As of rev 1.6, the required-limit side of the comparison sources from a validated, extracted document for all four counterparty types (Subagent 1 §05.1/05.2's four new classes), not admin-configured input alone — see §02's updated row. Automatic recalculation whenever placed coverage changes is a separate, Should/V2 capability (FR7.6) — at MVP, a coverage change triggers this engine's recompute the same way it triggers 06.1 and 06.2, or the merge's own race-condition fix only half-holds.

FR7, FR9, §6.7, §6.9

06.4 Config Change-Control Workflow Should

Gates changes to KPI thresholds, risk-score weights, and risk-appetite thresholds behind a logged rationale, review, and approval; versions each change so historical scores (06.1–06.3) keep the weights that were live when computed.

07 Subagent 3 — InsuranceCustodian Deterministic / Infra Mixed

Two functions that don't respond to a chat prompt — one runs on a schedule or on demand, the other is a passive log every other component writes to. Packaged together because one of Reporting's four outputs is a direct read of Audit's own state. Split release, this rev: a brief pass reclassified both functions to V2 together and flagged the resulting audit-log gap as an open item; this rev resolves it by splitting instead — 07.2 (Audit & Access Log) is back to MVP, 07.1 (Reporting & Export) stays V2.

Why split, not revert both to MVP: 07.2 is the one piece every other MVP function already assumes exists — append-only writes, no rendering/scheduling complexity, and every other spec in this plan states it writes atlas_write_audit unconditionally. 07.1 never had that kind of load-bearing dependency: it never carried an explicit §6 PRD tag to begin with, and nothing else in the roster structurally needs its rendered output to exist. The two functions still share one file — the §1 shared-dependency rationale (one of Reporting's four outputs reads Audit's own log) doesn't require them to share a release tag, the same way CoverageAnalyst's 06.1–06.3/06.4 split or RiskScanner's baseline/stretch split don't.
Two merges considered and rejected (historical): Alerts vs. Reporting look similar (both “outbound”) but one is event-triggered/near-real-time and the other is scheduled/on-demand document generation — different latency profile, different output shape; Alerts stayed with the orchestrator (§04.2) instead. Config Change-Control vs. Audit also look similar (both “governance”) but Config Change-Control is active, business-specific workflow while Audit is passive, universal infrastructure — collapsing them would bury generic audit logging inside one workflow's approval logic; Config Change-Control joined Subagent 2 instead (§06.4). Neither rejected pairing is what actually happened at the file level — the real groupings ran along the shared-dependency axis in §03's table.

09 Cross-cutting guardrails

These apply to every function above, agent or not, regardless of which of the five files it lives in:

Validation gate: a field stays “unconfirmed” and is excluded from every KPI calculation until a human validates it — no function may treat an unvalidated extraction as fact (§9.1).
Never silently overwrite: Subagent 1's Enrichment & Posting function (§05.3) must version every change; prior values stay retrievable with an audit entry (FR3.7). Subagent 3's Audit & Access Log function (§07.2), owner of app:audit_log, is MVP, so this guardrail holds in full from go-live.
Entity/site scoping: every query is filtered by the caller's role and assigned entity before it reaches a subagent — scoping the request, not just filtering the response after the fact — so an out-of-scope answer is never generated in the first place, not applied as an afterthought at the UI layer (§4.2).
News is advisory only: Subagent 4 (§08) may propose a signal and feed it as an optional, weighted risk-score input (FR6.6), but it never changes coverage or KPI data without a human confirming it (FR6.9).
Personal data is redacted by role, not just access-controlled: policy documents (D&O, GPA, workmen's compensation, etc.) contain named individuals' personal data. Every surface that can expose document content — the orchestrator's composed answers (§04), Subagent 1's stored/posted records (§05), and Subagent 3's generated packs (§07.1) — applies role-based redaction/masking for non-essential viewers, and export of underlying source documents is restricted to authorised roles only (§13, “Personal data handling”). No function in §04–08 currently owns this end-to-end; it needs an explicit owner before build.

10 State & data lifecycle

Atlas is closer to a ledger than a workflow tracker. Its “current” state is just the latest slice of an append-only history that has to stay reconstructable at any prior point in time — for a period tied to policy renewal and records-retention, not task completion. That's a different state-management burden than a shorter-lived case-workflow system, where state mostly matters while the case is open and can be archived once it closes.

The concrete risk this guards against: §10.3 (PRD) is explicit — “historical KPI and risk-score values retain the weights/thresholds in effect when they were calculated ... so a later reweighting does not silently rewrite history.” A risk-score weight changed in Subagent 2's Config Change-Control function (§06.4) eight months from now must never retroactively alter what a score was in March. That means 06.1–06.3 can't just be “read current data, compute, return an answer” — each one has to write an immutable, dated snapshot every time it computes, tagged to the configuration version that produced it (FR2.6, Should/V2, formalises this: “support point-in-time / historical KPI snapshots for trend and audit”).

Three clocks, not one: (1) the renewal-cycle clock — a policy's own inception–expiry window, typically annual for most lines in §17.4 but potentially multi-year for project-length covers like CAR/EAR; the PRD doesn't pin an exact duration, it's whatever the placed policy's own term is. (2) The regulatory-retention clock (§13: “retain documents and records per the Group records-retention policy”) — almost certainly longer than a single renewal cycle, but the PRD doesn't specify a duration either; worth adding to §18's open questions. (3) The audit clock, which doesn't really end during normal operation. Nothing should be archived or pruned before both (1) and (2) have elapsed, whichever is longer — and (3) never prunes at all under normal operation.
Migration is a fourth, temporary clock: §9.2's parallel-run requirement means Atlas's own state has to stay coherent and correct, unsupervised, for at least one full renewal cycle per entity before that entity's legacy tracker retires — a migration validation window measured in a policy term, not a sprint.
