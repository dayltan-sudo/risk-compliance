Only some of these components are agents; §02 draws the line.

01 Summary of the approach

The prototype already implies the shape of this system: a persistent chat panel with page-aware suggested prompts (promptsByPage, Atlas_App_UI v0.5.html:1678) that currently answers from a hard-coded lookup (chatExactReplies, :1734), and a page-scoped Action Items rail (actionItems, :1640) that is likewise static. The PRD specifies what both should become: a conversational assistant that answers only from live Atlas data and is fully traceable (FR8.3–FR8.4), fed by a document pipeline that turns broker/policy paperwork into validated records (FR3, §9), a ratio engine (FR2), a risk score (FR4, §10), and three newer registers — Contract Requirements (FR7), Insurance Exclusions (FR9), and News & Sector Intelligence (FR6).

That maps naturally onto one orchestrator that owns intent-routing, access control, and answer composition, plus three tiers of supporting components: a document-ingestion pipeline (event-driven, not conversational), a set of domain grounding services the orchestrator queries to answer questions, and a set of background/governance services that run on schedule or on data-change rather than in response to a prompt. Not all twelve are “agents” in the sense of something that reasons over ambiguous input — see §02.

Consolidation review (v1.1): the first pass over-separated several steps that were pipeline hops, not decision points. Three genuine merges bring the roster from 19 components to 12: the ingestion pipeline — PRD §9's seven stages, plus an eighth “Manual Questionnaire” item this plan's own v1.0 draft added on top — collapses to three (§05), Contract Requirements and Exclusion Conflict merge into one Contract Compliance Engine since the exclusion check is an override on the requirement's own status rather than an independent register (§06), and the Document/Validation Status component folds into the ingestion pipeline instead of standing alone. Coverage & Ratio vs. Risk Scoring, and Alerts vs. Reporting, and Config Change-Control vs. Audit were each considered and kept separate — different upstream dependencies or trigger models in every case, noted inline below.

02 Agent vs. workflow — what actually needs an LLM

Every component in §01 got called an “agent” in the first pass of this plan. Most of them aren't — they're deterministic pipelines that happen to be triggered by one. Worth separating cleanly, because the two categories have different engineering needs: agents need prompt design, evaluation, and human-in-the-loop guardrails; workflows just need to be correct and fast.

The test: does this component have to exercise judgement over ambiguous or unstructured input — infer intent, choose between options, interpret free text — or is it a fixed sequence of steps with one correct answer given the input? The second kind doesn't need an LLM in the loop at all, and for several of these components (the ratio and risk-score engines especially) that's a feature, not a gap: FR2.4 requires exact, reproducible calculation lineage, which is an argument against putting a non-deterministic model anywhere near the math.

04 The orchestrator

Owns the always-on assistant panel (§6.8, FR8) and the page-scoped Action Items rail (FR1.5). It never edits data — it is a read path only.

Atlas Assistant Orchestrator

Agent Must MVP

Intent + page-context routing — the prototype already scopes suggested prompts and Action Items by the page in view (currentPage, :1657; promptsByPage, :1678); the orchestrator formalises this by using page context as a prior on top of NL intent classification, so “which sites are under-insured” asked from Coverage Adequacy and from Global Map can route to the same Coverage & Ratio Engine with different default framing.

Access-scope gate — every query is filtered through the caller’s role and entity/site scope (§4.2) before it reaches a grounding service, so an Entity Risk Champion never receives an answer outside their assigned entity.

Answer composition with citations — every answer must trace back to the KPI, policy, or requirement record it came from (FR8.4). This replaces the prototype's static chatExactReplies strings (:1734) with live lookups plus a citation.

Explicit fallback — when no grounding service can answer, say so rather than guess (FR8.5) — the prototype's botReplyFor fallback string (:1780) is the right instinct and should carry forward verbatim as a behaviour, not just a copy string.

Hard constraint — decision-support only. No orchestrator path writes to a policy, coverage, requirement, or exclusion record; only the ingestion pipeline (§05) and a human validator can do that.

05 Document-analysis components

This is the literal “analyse documents and extract key information” pipeline — PRD §9's seven stages plus the manual fallback in FR3.9, consolidated to three deployable components. Only the extraction step inside the second one is actually agentic (§02). None post to the live database on their own; every path ends at a human validator.

Consolidated from 8 components to 3: the branching that exists (pass a document through, or fork it into the exception queue on failed classification/extraction, per §9.1) happens within a component's own confidence-threshold logic, not between deployable services — so most of the original stage-by-stage boundaries (Intake, Classification, Extraction, Validation Routing, Manual Questionnaire, Enrichment, Posting & Versioning, Recalculation) were hops, not independent decision points. Enrichment, Posting, and Recalculation in particular must fire together for every record with no exceptions (FR2.3 requires recalculation to follow a data change automatically) — splitting them risked a posted record whose KPIs silently failed to refresh if a message between components were lost. (Intake/Extraction/Validation do have different scaling profiles — I/O-bound upload, compute-heavy IDP, headcount-bound human review, all bursty at renewal season per the §13 scalability NFR — but that argues for independent scaling inside these three components, not for splitting them back into more deployable services.)

Note on data migration: back-book policies load through this exact same pipeline — there is deliberately no shortcut bypassing human validation for historical records (§9.2). The pipeline should be designed once and reused for both new intake and migration, sequenced by entity/BU. Two migration-specific rules the pipeline needs to enforce, not just the ordinary validation gate: a migrated record must clear the same completeness floor as the Data Completeness & Confidence KPI (§7.6) before it's treated as “live” — records below the floor stay in the exception queue rather than being silently included — and each entity runs Atlas in parallel with its existing local tracker for at least one renewal cycle before that tracker is retired, to catch migration gaps (§9.2).

06 Domain grounding components

These are what the orchestrator actually queries to answer a question or populate a dashboard view. Each owns one register from the data model (§8.1) and is the single place that register's business logic lives. Renamed from “Agent” to “Engine” below wherever §02 found no agentic reasoning in it — only News & Sector Intelligence keeps the name.

Merged: Contract Requirements and Exclusion Conflict are now one Contract Compliance Engine. §6.9 doesn't describe two independent registers that happen to interact — it describes one status decision (Met / At-risk / Gap / Excluded) where the exclusion check is an override on the requirement check. As two separate components this needs strict ordering (exclusions must always evaluate after every requirement recalc) and a tie-break rule for who wins on disagreement; as one component with one status field, that race condition doesn't exist. The Document/Validation Status component is also gone from this tier — it never owned a register, it read the ingestion pipeline's own queue state, so the orchestrator now queries the pipeline (§05) directly instead of through a second, potentially-stale copy.

07 Background & governance components

These don't respond to a chat prompt — they run on a schedule or fire on a data event, and several of them are gates the other components must pass through rather than destinations in their own right. Unlike §05 and §06, none of these four merge with each other — and none of them are agents.

Two merges considered and rejected here: Alerts vs. Reporting look similar (both “outbound”) but one is event-triggered/near-real-time and the other is scheduled/on-demand document generation — different latency profile, different output shape. Config Change-Control vs. Audit also look similar (both “governance”) but Config Change-Control is active, business-specific workflow (propose → review → approve → version) while Audit is passive, universal infrastructure every component writes to — collapsing them would bury generic audit logging inside one workflow's approval logic. Both pairs stay separate.

Alerts & Notification

Workflow Must*

Evaluates the §12.1 trigger table — renewal due, coverage gap, low-confidence extraction, carrier downgrade, aggregate erosion, new hotspot, emerging-risk breach, contractual gap, exclusion conflict — and routes to the right recipient over the right channel (in-app, email, Teams). *§12.1's trigger table itself carries no per-row MoSCoW/release tags; only the contractual-gap (FR7.5) and exclusion-conflict (FR9.5) triggers are directly traceable to a Must/MVP requirement, and the emerging-risk trigger depends on FR6.8 (Must/V2). The component is MVP-relevant from day one, but not every trigger it evaluates ships at MVP — see §09.

08 Cross-cutting guardrails

These apply to every component above, agent or not:

Validation gate: a field stays “unconfirmed” and is excluded from every KPI calculation until a human validates it — no component may treat an unvalidated extraction as fact (§9.1).
Never silently overwrite: the Enrichment & Posting workflow must version every change; prior values stay retrievable with an audit entry (FR3.7).
Entity/site scoping: every query is filtered by the caller's role and assigned entity before it reaches a grounding service — scoping the request, not just filtering the response after the fact — so an out-of-scope answer is never generated in the first place, not applied as an afterthought at the UI layer (§4.2).
News is advisory only: the News & Sector Intelligence Agent may propose a signal and feed it as an optional, weighted risk-score input (FR6.6), but it never changes coverage or KPI data without a human confirming it (FR6.9).
Personal data is redacted by role, not just access-controlled: policy documents (D&O, GPA, workmen's compensation, etc.) contain named individuals' personal data. Every surface that can expose document content — the orchestrator's composed answers, the ingestion pipeline's stored records, and Reporting & Export's generated packs — applies role-based redaction/masking for non-essential viewers, and export of underlying source documents is restricted to authorised roles only (§13, “Personal data handling”). No component in §05–07 currently owns this end-to-end; it needs an explicit owner before build.

09 State & data lifecycle

Atlas is closer to a ledger than a workflow tracker. Its “current” state is just the latest slice of an append-only history that has to stay reconstructable at any prior point in time — for a period tied to policy renewal and records-retention, not task completion. That's a different state-management burden than a shorter-lived case-workflow system, where state mostly matters while the case is open and can be archived once it closes.

The concrete risk this guards against: §10.3 is explicit — “historical KPI and risk-score values retain the weights/thresholds in effect when they were calculated ... so a later reweighting does not silently rewrite history.” A risk-score weight changed in Config Change-Control eight months from now must never retroactively alter what a score was in March. That means Coverage & Ratio Engine, Risk Scoring Engine, and Contract Compliance Engine (§06) can't just be “read current data, compute, return an answer” — each one has to write an immutable, dated snapshot every time it computes, tagged to the configuration version that produced it (FR2.6, Should/V2, formalises this: “support point-in-time / historical KPI snapshots for trend and audit”).

Three clocks, not one: (1) the renewal-cycle clock — a policy's own inception–expiry window, typically annual for most lines in §17.4 but potentially multi-year for project-length covers like CAR/EAR; the PRD doesn't pin an exact duration, it's whatever the placed policy's own term is. (2) The regulatory-retention clock (§13: “retain documents and records per the Group records-retention policy”) — almost certainly longer than a single renewal cycle, but the PRD doesn't specify a duration either; worth adding to §18's open questions. (3) The audit clock, which doesn't really end during normal operation. Nothing should be archived or pruned before both (1) and (2) have elapsed, whichever is longer — and (3) never prunes at all under normal operation.
Migration is a fourth, temporary clock: §9.2's parallel-run requirement means Atlas's own state has to stay coherent and correct, unsupervised, for at least one full renewal cycle per entity before that entity's legacy tracker retires — a migration validation window measured in a policy term, not a sprint.
